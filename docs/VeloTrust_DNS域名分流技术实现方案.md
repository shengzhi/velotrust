# VeloTrust DNS 域名分流技术实现方案

## 1. 文档说明

### 1.1 文档目标

本文定义 VeloTrust 企业自托管零信任访问平台中，基于域名后缀的客户端 DNS
分流功能的架构、业务流程、关键技术、平台接管方式、异常处理和验收要求。

本文采用以下确定的设计原则：

-   企业内部域名后缀对应的 DNS 查询只能发送到配置的企业 DNS。
-   不匹配任何企业内部域名规则的查询，发送到终端原有 DNS 解析路径。
-   企业 DNS 故障时，内部域名查询失败关闭（Fail
    Closed），禁止回退到终端原有 DNS 或公共 DNS。
-   域名分流策略由 VeloTrust 控制面统一管理并下发，客户端 DNS
    代理负责执行。
-   DNS 解析成功不代表访问授权成功；业务连接仍须经过 WireGuard
    路由、网关 ACL 和 VeloTrust 访问策略控制。
-   本文面向单企业独立部署场景，不设计多租户策略隔离。

### 1.2 术语

  ----------------------------------------------------------------------------------------------------
  术语                                说明
  ----------------------------------- ----------------------------------------------------------------
  本地 DNS 代理                       运行在终端上的 DNS 服务，接收操作系统转交的 DNS 查询并选择上游
                                      DNS

  企业 DNS                            企业内部 DNS
                                      服务器，负责解析企业内部域名，可部署在企业网络或受控网关侧

  终端原有 DNS                        客户端接管前从当前网络环境获取的 DNS
                                      配置，例如办公网络、家庭路由器或运营商下发的 DNS

  内部域名规则                        由管理员配置的域名后缀，如 `internal.example.com`

  域名分流                            根据查询域名匹配规则，选择企业 DNS 或终端原有 DNS

  DNS 接管                            将操作系统的常规 DNS 请求可靠地交给本地 DNS 代理处理

  失败关闭                            安全策略无法正常执行时拒绝请求，而不是自动切换到不受信任的路径

  策略版本                            控制面生成并下发的 DNS 配置版本，用于客户端状态确认和故障排查
  ----------------------------------------------------------------------------------------------------

## 2. 设计目标与非目标

### 2.1 设计目标

1.  为企业内部域名提供统一、稳定的企业 DNS 解析路径。
2.  使普通互联网域名继续使用终端原有 DNS，减少企业 DNS
    负载和不必要的查询转发。
3.  避免内部域名因企业 DNS 超时、隧道断开或配置异常而泄漏到公共 DNS。
4.  支持 Windows、macOS、Linux 的平台适配，并为后续移动端扩展预留接口。
5.  支持 DNS 策略版本管理、配置应用确认、健康检测、审计和故障恢复。
6.  将 DNS 解析策略与网络访问授权解耦，保持零信任策略的最终执行边界。

### 2.2 非目标

本功能本身不负责：

-   替代企业 DNS 的权威解析、递归解析或域名管理能力。
-   仅通过 DNS 解析结果决定用户是否可以访问业务资源。
-   在不使用操作系统网络过滤能力的情况下，保证能够拦截所有应用自建的
    DoH、DoT 或自行发送的 DNS 流量。
-   将任意外部域名强制通过企业 DNS 解析。
-   代替 WireGuard 隧道、路由和网关 ACL。

## 4. DNS 分流策略

### 4.1 规则定义

管理员配置一个或多个企业内部域名后缀。例如：

-   `internal.example.com`
-   `corp.example.com`

规则匹配应遵循 DNS 标签边界，而不是简单字符串后缀比较。

  查询域名                     是否匹配 `internal.example.com`
  ---------------------------- ---------------------------------
  `git.internal.example.com`   是
  `internal.example.com`       是
  `evilinternal.example.com`   否
  `example.com`                否

域名比较时应忽略大小写，并将国际化域名统一转换为一致的 ASCII/IDNA
表示后再匹配。域名末尾的根点应规范化处理。匹配规则必须避免将相似字符串误判为企业域名。

### 4.2 匹配优先级

当存在多个后缀规则时，采用最长匹配优先。例如：

-   `example.com`
-   `internal.example.com`

查询 `git.internal.example.com` 时，选择更具体的 `internal.example.com`
规则。

在当前策略模型中，所有内部域名规则均使用企业
DNS，最长匹配主要用于未来支持不同企业
DNS、网络区域或策略参数时消除歧义。

### 4.3 路由决策

代理收到查询后，按以下顺序处理：

1.  验证 DNS 消息格式及请求类型。
2.  规范化查询域名。
3.  检查缓存；缓存键必须包含域名、记录类型、记录类和必要的策略版本/规则上下文。
4.  通过域名规则匹配器判断是否属于企业内部域名。
5.  命中内部域名规则：只选择企业 DNS 上游。
6.  未命中内部域名规则：选择终端原有 DNS 上游。
7.  转发请求，处理响应、超时和重试。
8.  根据 DNS 响应语义更新缓存并返回客户端。
9.  按审计配置记录必要的运行事件。

### 4.4 内部域名禁止回退

内部域名命中规则后，DNS 上游选择即被锁定为企业
DNS。以下情况均不得转发到终端原有 DNS：

-   企业 DNS 超时。
-   WireGuard 隧道断开。
-   企业 DNS 返回 `SERVFAIL`。
-   企业 DNS 连接失败或目标不可达。
-   企业 DNS 返回 `NXDOMAIN`。
-   企业 DNS 对指定记录类型返回 `NOERROR` 但没有答案（NODATA）。

处理方式：

-   对 `NXDOMAIN` 和 NODATA，按 DNS 协议语义返回企业 DNS 的否定结果。
-   对超时、连接失败或 `SERVFAIL`，按代理实现返回适当的 DNS
    失败响应，并记录具体错误原因。
-   不得因故障自动将内部域名查询发送到公共 DNS 或终端原有 DNS。

### 4.5 外部域名处理

未匹配任何内部域名后缀的域名，应通过终端原有 DNS 路径解析。

"终端原有
DNS"需要由平台适配器从当前活动网络配置中发现和维护，不能硬编码为
`8.8.8.8`、`1.1.1.1` 等公共 DNS。若终端原有 DNS 发生变化，例如 Wi-Fi
切换或 DHCP 更新，客户端应更新代理的上游配置。

原有 DNS 不可用时，默认按原有 DNS 失败处理；不得擅自改为企业
DNS，除非后续产品策略明确增加此能力。

## 5. 端到端业务流程

### 5.1 客户端启动与 DNS 接管

1.  客户端完成自身初始化，并读取本地持久化状态。
2.  检查 DNS 代理运行环境、监听端口和必要权限。
3.  获取并保存当前系统 DNS 配置及配置来源信息。
4.  从控制面获取当前有效 DNS 策略，并验证策略版本和完整性。
5.  启动本地 DNS 代理，加载内部域名后缀和企业 DNS 上游。
6.  通过平台 DNS 接管适配器，将系统 DNS 查询导入本地代理。
7.  执行接管验证，确认系统查询实际进入代理。
8.  验证企业 DNS 的路由可达性；该检测仅用于状态判断，不允许用公共 DNS
    代替企业 DNS。
9.  客户端向控制面上报策略版本、DNS 接管状态、企业 DNS
    健康状态和错误信息。

如果代理未启动、策略不完整或接管验证失败，客户端不得报告 DNS
功能已生效。根据产品的安全配置，可以阻止建立受保护网络访问，或进入明确标识的受限状态；不得静默回退为不受控的
DNS 行为。

### 5.2 内部域名查询流程

以 `git.internal.example.com` 为例：

1.  应用向操作系统发起 DNS 查询。
2.  操作系统将查询交给本地 DNS 代理。
3.  代理规范化域名并匹配 `internal.example.com`。
4.  代理选择企业 DNS 地址，并确认该地址应通过 WireGuard 可达。
5.  代理向企业 DNS 转发查询。
6.  企业 DNS 返回解析结果。
7.  代理按 TTL 规则缓存结果并返回应用。
8.  应用使用解析得到的 IP 建立独立业务连接。
9.  业务连接仍由 WireGuard 路由、网关 ACL 和访问策略决定是否允许。

如果步骤 4 或 5 发生故障，代理返回失败，不尝试终端原有 DNS。

### 5.3 外部域名查询流程

以 `www.example.net` 为例：

1.  应用向操作系统发起 DNS 查询。
2.  操作系统将查询交给本地 DNS 代理。
3.  代理匹配内部域名规则，确认没有命中。
4.  代理选择终端当前原有 DNS 上游。
5.  代理向原有 DNS 转发查询。
6.  代理缓存有效响应并返回应用。

外部域名查询不需要先访问企业 DNS。

### 5.4 网络切换流程

当终端从办公网络切换到家庭网络、Wi-Fi 切换到有线网络，或 DHCP 更新 DNS
配置时：

1.  平台适配器检测网络变化。
2.  获取新的活动网络 DNS 配置。
3.  更新"终端原有 DNS"上游集合。
4.  保留企业域名后缀规则和企业 DNS 目标。
5.  检查 WireGuard 隧道、企业 DNS 路由和必要 ACL。
6.  更新本地代理配置并切换版本。
7.  对外部 DNS 上游执行健康检测。
8.  上报变更结果。

更新过程中应采用原子切换，避免代理短暂进入没有可用上游的中间状态。内部域名始终只能选择企业
DNS。

### 5.5 策略更新流程

1.  管理员在控制台修改内部域名后缀或企业 DNS 地址。
2.  控制面验证域名格式、地址、端口和策略冲突。
3.  控制面生成新的单调递增策略版本。
4.  客户端通过认证通道获取新策略。
5.  客户端验证策略完整性和版本。
6.  本地代理先构建新规则集，再以原子方式切换。
7.  客户端执行规则匹配和 DNS 可达性检查。
8.  客户端上报已应用版本或失败原因。
9.  控制面区分"已发送""已接收"和"已生效"，必要时重试或告警。

新策略应用失败时，不应把内部域名转为外部 DNS
路径。客户端可以继续使用最后一个已验证的有效策略；若该策略已失效或被控制面明确撤销，则应进入失败关闭状态。

## 6. Go 本地 DNS 代理设计

### 6.1 推荐组件

Go 实现可采用模块化结构。DNS 协议库可选用成熟的 Go DNS 实现，例如
`github.com/miekg/dns`，具体版本应由项目依赖管理和安全评估确定。

``` text
internal/dnsproxy/
  server.go           # 本地 DNS UDP/TCP 服务生命周期
  handler.go          # 查询处理主流程
  normalize.go        # 域名规范化与校验
  matcher.go          # 内部域名后缀匹配
  forwarder.go        # 上游 DNS 转发
  cache.go            # 正缓存和负缓存
  policy.go           # DNS 策略模型与原子更新
  health.go           # 上游和代理健康检查
  metrics.go          # 指标
  audit.go            # 审计事件
  platform/
    interface.go      # 平台接管接口
    windows/          # Windows 适配
    darwin/           # macOS 适配
    linux/            # Linux 适配
```

### 6.2 处理接口示例

``` go
type UpstreamKind string

const (
    UpstreamEnterprise UpstreamKind = "enterprise"
    UpstreamOriginal   UpstreamKind = "original"
)

type DNSPolicy struct {
    Version            uint64
    InternalSuffixes   []string
    EnterpriseUpstreams []string
    OriginalUpstreams   []string
}

type RouteDecision struct {
    Kind       UpstreamKind
    Upstreams  []string
    MatchedRule string
}

type DNSRouter interface {
    Decide(qname string) (RouteDecision, error)
}
```

以上代码仅用于说明接口边界，不是完整实现。生产实现还需要校验上游地址、限制策略大小、处理
IPv4/IPv6、支持 UDP/TCP
DNS、控制超时和并发，并为配置更新建立不可变快照或其他并发安全机制。

### 6.3 规则匹配要求

域名匹配器应：

-   对域名进行大小写规范化。
-   处理末尾根点。
-   拒绝非法域名格式和空规则。
-   正确处理 IDNA 域名。
-   使用标签边界匹配，避免 `evilinternal.example.com` 被误判。
-   支持多个规则的最长匹配。
-   对不存在规则的域名明确返回外部 DNS 路径，而不是企业 DNS。
-   采用不可变规则快照，避免并发请求读取到部分更新的配置。

### 6.4 上游转发

转发器至少需要支持：

-   DNS over UDP。
-   DNS over TCP，处理截断响应或上游要求 TCP 的情况。
-   可配置连接和响应超时。
-   有上限的重试次数。
-   并发请求控制和重复查询合并。
-   对不同上游的健康状态进行独立统计。
-   记录上游类型、耗时、错误类型和重试次数。
-   防止请求循环转发，例如本地代理把请求转给系统 DNS，而系统 DNS
    又指向本地代理。

企业 DNS 与终端原有 DNS
必须使用独立的上游集合和路由决策。企业域名的失败路径中不能出现原有 DNS
上游。

### 6.5 缓存设计

缓存应至少考虑：

-   正向答案缓存。
-   NXDOMAIN 等负缓存。
-   NODATA 结果缓存。
-   TTL 到期。
-   DNS 策略版本变更。
-   内部域名规则变更后的缓存失效。
-   不同记录类型（A、AAAA、CNAME、SRV 等）的独立缓存语义。
-   并发相同查询合并，避免缓存未命中时放大上游流量。

不能因为缓存中存在旧的内部域名答案，就在访问策略已撤销后继续允许业务访问。DNS
缓存只影响解析，不代替 ACL
或授权决策。对于内部资源地址变化或策略变更，应根据安全要求主动清理受影响缓存。

### 6.6 错误映射

DNS 代理应区分协议响应和本地传输故障：

  -----------------------------------------------------------------------
  情况                                处理
  ----------------------------------- -----------------------------------
  企业 DNS 返回有效答案               原样或按协议允许的方式返回响应

  企业 DNS 返回 NXDOMAIN              返回 NXDOMAIN，不回退

  企业 DNS 返回 NODATA                返回相应否定结果，不回退

  企业 DNS 返回 SERVFAIL              返回失败，不回退

  企业 DNS 超时或网络不可达           记录故障并返回 SERVFAIL
                                      或适当失败响应，不回退

  原有 DNS 不可达                     外部查询失败，不自动切换到企业 DNS

  查询消息格式错误                    返回 FORMERR 或按协议处理

  不支持的操作码或类型                按 DNS 协议和实现能力返回相应错误
  -----------------------------------------------------------------------

## 7. 平台 DNS 接管

本地代理只有在操作系统查询确实进入代理时才有意义。平台接管必须作为独立模块设计，并提供应用、验证和恢复流程。

### 7.1 Windows

可分阶段实施：

**基础方案**

1.  由客户端以管理员权限配置受管网络接口的 DNS。
2.  本地代理监听受控的本地地址和端口。
3.  检测所有活动接口的 DNS 配置及网络变化。
4.  使用系统 DNS 查询进行端到端验证。
5.  在客户端退出时，谨慎恢复接管前配置。

需要评估 Windows DNS Client、NRPT、多个活动网卡、VPN
冲突和端口占用。仅修改 WireGuard 虚拟网卡的 DNS
不一定能让所有系统查询进入代理。

**增强方案**

如果要求强制拦截自行发送的 UDP/TCP 53 查询，可评估 Windows Filtering
Platform（WFP）等网络过滤机制。此方案涉及更高权限、系统组件、安装签名、兼容性和故障恢复，应单独进行设计与安全评估。

### 7.2 macOS

优先评估 Apple Network Extension 能力。若产品要求由系统把 DNS
请求交给自定义代理，应验证 DNS Proxy Provider
及相关授权、签名和部署要求。通过 VPN 配置 DNS 服务器与接入自定义 DNS
代理是不同方案，不能混为一谈。

不建议仅修改 `/etc/resolv.conf`
作为正式接管机制。应实现系统状态检测、网络变化处理、配置恢复和扩展失效告警。

### 7.3 Linux

按发行版和网络管理方式适配：

-   `systemd-resolved` 环境可通过受支持的接口配置 DNS 和路由域。
-   NetworkManager 管理网络的系统应通过相应网络管理接口集成。
-   没有 `systemd-resolved` 的系统需要独立适配。
-   容器、网络命名空间和应用自带解析器需要单独评估。

如果目标是"查询进入 Go
本地代理"，则应配置系统解析路径指向代理，而不是简单地把
`systemd-resolved` 的某个接口直接配置成企业
DNS。必须防止系统解析器与本地代理之间形成循环转发。

### 7.4 移动端扩展

Android 可评估 `VpnService` 等系统能力；iOS/iPadOS 应评估 Network
Extension 中适用的 DNS Proxy 或 VPN DNS
机制。移动平台权限、签名、系统版本及应用商店分发要求不同，应作为单独阶段实施。

### 7.5 平台适配接口

``` go
type DNSController interface {
    CheckSupport() error
    Capture() error
    Apply(proxyAddress string) error
    Verify() error
    Restore() error
}
```

接口语义：

-   `CheckSupport`：检查系统版本、权限、网络服务和接管能力。
-   `Capture`：保存接管前 DNS 配置及配置所有权信息。
-   `Apply`：应用系统 DNS 接管配置。
-   `Verify`：验证系统查询进入代理，不能只检查配置命令是否执行成功。
-   `Restore`：在安全条件满足时恢复原有配置。

`Restore`
不应盲目覆盖用户或其他软件在接管期间修改的配置。应比较当前状态、客户端记录的期望状态和保存的原始状态，避免破坏其他网络管理工具的配置。

## 8. WireGuard 与路由要求

企业 DNS 应使用可经 WireGuard 到达的地址。配置时需要检查：

1.  企业 DNS 地址是否位于预期企业网络或隧道可达网络。
2.  WireGuard Peer 的 `AllowedIPs` 是否覆盖企业 DNS 地址。
3.  操作系统路由是否确实将企业 DNS 流量发送到 WireGuard。
4.  网关防火墙和 ACL 是否允许客户端到企业 DNS 的 UDP/TCP 53 流量。
5.  企业 DNS 的回程路由是否正确。
6.  DNS 地址是否与终端本地网段、隧道地址池或其他路由冲突。
7.  IPv4 与 IPv6 的 DNS 路径是否都符合策略。

WireGuard 的 `AllowedIPs` 本身不实现域名分流。域名后缀分流由本地 DNS
代理完成，IP 流量路由由操作系统路由表和 WireGuard 配置完成。DNS
解析成功后，访问业务 IP 仍须经过访问策略和 ACL。

## 9. 控制面策略模型与配置下发

### 9.1 配置示例

``` yaml
dns_policy:
  version: 12
  mode: suffix_split
  internal_domains:
    - internal.example.com
    - corp.example.com
  enterprise_upstreams:
    - address: 10.200.0.1
      port: 53
      protocol: udp
    - address: 10.200.0.1
      port: 53
      protocol: tcp
  external_resolution:
    mode: original_system_dns
  internal_failure:
    fallback: deny
    return_servfail_on_transport_error: true
  cache:
    enabled: true
  audit:
    record_policy_match: true
    record_query_name: configurable
```

这是建议的配置结构示例。实际协议需要进一步定义字段校验、默认值、版本兼容和签名/完整性验证。`internal_failure.fallback`
应由服务端固定为 `deny`
或采用等效的不可绕过约束，不能允许客户端因临时故障自行放宽。

### 9.2 配置验证

控制面应在发布前验证：

-   域名后缀合法、规范化后不重复。
-   企业 DNS 地址和端口有效。
-   企业 DNS 地址具有预期的网络归属。
-   DNS 规则没有歧义或非法通配表达式。
-   规则数量和配置大小在限制内。
-   策略版本单调递增。
-   配置可以被目标客户端版本识别。
-   变更具有操作者身份和审计记录。

### 9.3 客户端状态

客户端应上报至少以下状态：

-   当前接收的策略版本。
-   当前实际应用的策略版本。
-   DNS 代理运行状态。
-   系统 DNS 接管状态。
-   最近一次接管验证时间和结果。
-   企业 DNS 可达性状态。
-   当前原有 DNS 上游摘要。
-   最近错误类型和发生时间。

控制面不能将"配置已发送"直接视为"配置已生效"，应区分发送、接收、验证、应用和运行健康状态。

## 10. 安全控制

### 10.1 DNS 泄漏保护

-   内部域名命中规则后，禁止选择原有 DNS 上游。
-   企业 DNS 不可达时，不自动使用公共 DNS。
-   WireGuard 隧道断开时，内部 DNS 查询失败关闭。
-   策略未同步或校验失败时，不得以外部 DNS 替代企业 DNS。
-   代理启动失败时，不得将系统 DNS 留在失效的本地地址而不告警。
-   对自行发送 DNS、DoH、DoT
    的应用，按企业安全等级决定是否部署系统级网络过滤或终端限制。

### 10.2 DNS 接管与访问授权分离

DNS 仅负责名称解析。解析出内部资源 IP 后，仍需由 WireGuard 路由、网关
ACL 和 VeloTrust
策略引擎执行访问限制。不能把"域名已解析"当作"访问已授权"。

### 10.3 缓存与撤销

DNS 缓存不应延长授权有效期。资源授权撤销后，数据面 ACL
应及时生效，即使终端缓存中仍然存在 IP 地址。域名规则变更时，应清理相关
DNS 缓存并更新代理规则版本。

### 10.4 日志与隐私

建议记录策略版本、命中规则、上游类型、响应码、耗时、错误类型和终端标识。完整查询域名可能包含敏感业务信息，应允许按企业策略配置日志粒度、保留期限和访问权限，并避免记录不必要的个人数据。

## 12. 可观测性与运维

### 12.1 建议指标

-   DNS 请求总量，按内部/外部分类。
-   按上游类型统计的请求量、成功量、失败量。
-   企业 DNS 响应耗时分布。
-   原有 DNS 响应耗时分布。
-   DNS 超时、SERVFAIL、NXDOMAIN、NODATA 数量。
-   内部域名故障时的回退尝试计数，目标值必须为零。
-   系统 DNS 接管验证成功率。
-   当前策略版本与已应用版本不一致的终端数。
-   本地代理重启次数和端口冲突次数。

### 12.2 告警建议

-   企业 DNS 连续探测失败。
-   客户端 DNS 接管验证失败。
-   终端仍使用已失效的本地代理地址。
-   客户端策略版本长期落后于控制面。
-   检测到内部域名查询尝试使用非企业上游。
-   系统网络变更后外部 DNS 上游未能更新。
-   WireGuard 已断开但客户端仍尝试将内部 DNS 请求发送到非企业路径。

## 13. 测试与验收

### 13.1 功能测试

1.  内部域名命中后只访问企业 DNS。
2.  外部域名只访问终端原有 DNS，不先访问企业 DNS。
3.  域名大小写不同仍能正确匹配。
4.  带末尾根点的域名能正确匹配。
5.  相似但不属于内部后缀的域名不会误匹配。
6.  多条后缀规则按照最长匹配执行。
7.  UDP 与 TCP DNS 查询均按相同规则分流。
8.  A、AAAA、CNAME 及常见记录类型的响应处理符合预期。
9.  原有 DNS 随网络切换变化后，外部查询使用新上游。

### 13.2 安全测试

1.  企业 DNS 超时，内部域名查询失败且没有任何公共 DNS 收到该查询。
2.  WireGuard 断开，内部域名查询失败且不发生回退。
3.  企业 DNS 返回 NXDOMAIN，内部查询不发往原有 DNS。
4.  策略缺失或版本校验失败时，不允许内部域名走外部 DNS。
5.  本地代理崩溃后，系统不会长期指向无人监听的 DNS 地址而无告警。
6.  恢复系统 DNS 时，不覆盖接管期间其他软件或用户作出的有效修改。
7.  通过抓包验证企业 DNS 请求走预期 WireGuard 路径。
8.  验证自行发送 UDP/TCP 53、DoH 和 DoT
    的应用是否被允许；测试结果应与企业所选安全级别一致。
9.  验证 DNS 解析成功但 ACL 拒绝访问时，业务连接仍被正确阻止。
10. 验证策略更新后旧缓存不会造成不符合当前规则的解析行为。

### 13.3 验收标准

-   所有配置的内部域名后缀均稳定路由至企业 DNS。
-   非内部域名按终端原有 DNS 路径解析。
-   内部域名在企业 DNS 故障、隧道断开和策略异常时均不发生 DNS 上游回退。
-   各目标操作系统均有可重复的接管验证和恢复测试。
-   控制面能够区分策略已发送、已接收、已应用和已验证。
-   关键错误有可观测指标、日志和告警。
-   DNS 解析与访问授权相互独立，ACL 能继续执行最终访问控制。

具体性能指标、终端规模、故障恢复时间和日志保留周期，应在目标部署规模与压测结果明确后制定，不在缺少基准数据时承诺固定数值。

### 第一阶段：基础 DNS 代理

## 15. 最终设计结论

VeloTrust 采用基于域名后缀的 DNS 分流架构：

1.  内部域名后缀走企业 DNS。
2.  其他域名走终端原有 DNS。
3.  企业 DNS 故障时，内部域名失败关闭，绝不回退到公共 DNS。
4.  DNS 代理统一实现分流策略，操作系统适配层负责确保系统查询进入代理。
5.  WireGuard 负责加密传输与网络路由，不负责域名后缀匹配。
6.  DNS 解析不等同于访问授权，最终访问仍由 VeloTrust 策略和数据面 ACL
    控制。
7.  控制面通过策略版本、配置确认、健康检查、审计和状态对账确保客户端策略持续有效。

这套设计将 DNS
分流、安全边界、平台差异和运维能力分开管理，既能满足企业内部域名解析需求，也能在企业
DNS 或隧道故障时避免内部域名泄漏。
