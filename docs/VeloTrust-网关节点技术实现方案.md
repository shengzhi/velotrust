# VeloTrust 网关节点功能需求与技术详细实现方案（实现更新版）

- 文档版本：V1.1（Gateway Agent 核心数据面实现更新）
- 适用产品：VeloTrust 企业级零信任安全访问平台（ZTNA）
- 适用部署：企业自托管、单企业部署
- 核心技术：Go、WireGuard、HTTPS/gRPC、Linux 网络管理接口
- 文档范围：网关节点功能需求、独立运行架构、注册与身份、网络与隧道、配置执行、安全控制、测试验收，以及最后阶段的控制面与管理控制台集成

## 一、文档目标与设计原则

### 1.1 文档目标

本文档定义 VeloTrust 网关节点的业务功能需求和技术实现方案，作为网关 Agent、控制面网关管理能力、网络编排及后续管理控制台集成的开发依据。

网关节点是企业终端访问内部业务资源时的重要网络边界。它需要建立可信的节点身份，维护安全隧道，按照有效授权执行路由与访问过滤，并能够报告自身配置和运行状态。网关不应只是一个 WireGuard 启动脚本，也不能仅凭隧道建立成功就允许业务流量通过。

### 1.2 设计原则

1. **控制面与数据面分离。** 控制面负责节点管理、身份校验、策略决策、网络编排和配置分发；网关负责在本机落实已批准的网络配置及访问规则。
2. **先独立实现，再集成控制台。** 网关核心功能应通过本地配置、命令行、独立 API 或模拟控制面完成开发和测试。管理控制台的页面和交互集成安排在最后阶段。
3. **最小权限与默认拒绝。** 网关仅转发明确获准的流量。未配置或无法验证的访问不得默认放行。
4. **每个节点使用一个长期密钥对。** WireGuard 公钥同时作为节点的网络身份标识和隧道 Peer 标识。控制面必须先通过注册凭证等机制验证节点，再将已验证的节点记录绑定到该公钥；WireGuard 密钥本身不用于数字签名或替代控制面身份认证。
5. **期望状态与实际状态分离。** 控制面下发配置不代表配置已经生效；网关必须核验本机实际状态并回报应用结果。
6. **配置变更以数据库当前状态为准。** 网络配置通过内容摘要校验，支持幂等应用和失败恢复；不维护配置业务版本或旧配置快照。
7. **安全策略可撤销。** 节点隔离、授权撤销、密钥失效等操作必须最终落实到 Peer、路由、ACL 和防火墙规则。
8. **面向企业自托管。** 本方案不设计多租户体系，不包含租户级隔离、租户配额或租户间管理。不同企业之间的隔离由独立部署边界实现。

### 1.3 术语说明

| 术语 | 说明 |
|---|---|
| Gateway Node | 网关节点，是企业网络中的受管节点，可承载终端到企业资源的受控转发 |
| Gateway Agent | 部署在网关服务器上的 Go 语言常驻进程，负责节点身份、控制通道、配置执行和状态上报 |
| 控制面 | VeloTrust 服务端的节点管理、身份、策略、网络编排、配置分发等能力 |
| 数据面 | WireGuard 隧道、本机路由、ACL、防火墙和流量转发机制 |
| Peer | WireGuard 中的对端节点配置 |
| AllowedIPs | WireGuard Peer 的允许地址集合，同时参与路由选择和源地址约束；不能单独替代业务授权 |
| 期望配置 | 控制面根据当前拓扑和授权策略计算出的目标配置 |
| 实际配置 | 网关操作系统及 WireGuard 当前真实生效的配置 |
| 注册凭证 | 供新网关首次注册使用的限时、限次凭证，不是长期运行身份 |
| 配置摘要 | 对完整配置内容计算的摘要；用于幂等应用和期望/实际状态比对，不递增 |

## 二、网关节点功能需求

### 2.1 功能范围

网关节点模块负责以下能力：

- 网关节点创建、注册、审批、激活、停用、隔离和注销。
- Gateway Agent 安装、启动、停止、升级及运行状态管理。
- 节点身份认证、密钥保护、密钥轮换和撤销。
- WireGuard 接口、Peer、隧道地址、Endpoint 和连接状态管理。
- 网络地址规划、路由管理、访问控制和必要的 NAT。
- 配置校验、摘要校验、应用确认、重试和状态对账。
- 控制通道健康、隧道健康、资源可达性和系统资源监控。
- 运行日志、安全审计、异常告警和故障恢复。
- 与控制面及管理控制台的集成；该项在核心功能验证完成后实施。

网关不负责替代用户认证、终端设备注册、业务资源目录和访问策略业务管理。相关能力由 VeloTrust 控制面提供，网关接收经过认证和校验的配置并在数据面执行。

### 2.2 功能需求清单

|---|---|---|---|
| GW-001 | 节点基础管理 | 支持创建、查询、修改、启用、停用、隔离和注销节点 | P0 |
| GW-002 | Agent 运行 | 支持进程启动、退出、重启、自检和本地配置加载 | P0 |
| GW-003 | 本地身份 | 生成唯一的 WireGuard 节点密钥，并安全保存本地私钥 | P0 |
| GW-004 | 注册机制 | 支持限时、限次、可撤销的一次性注册凭证 | P0 |
| GW-005 | 注册校验 | 校验节点绑定、凭证有效性、公钥冲突和注册状态 | P0 |
| GW-006 | 审批与激活 | 支持人工审批或可配置的自动激活策略；默认建议人工审批 | P0 |
| GW-007 | WireGuard 管理 | 支持接口、Peer、Endpoint、AllowedIPs 和隧道地址管理 | P0 |
| GW-008 | 网络路由 | 支持经校验的路由创建、更新、删除及冲突检测 | P0 |
| GW-009 | 访问控制 | 将有效授权转换为 ACL/防火墙规则，并落实默认拒绝 | P0 |
| GW-010 | 流量转发 | 在已批准的网络范围内转发终端与企业资源之间的流量 | P0 |
| GW-011 | 配置收敛 | 支持期望配置摘要、实际应用摘要、应用确认和状态对账 | P0 |
| GW-012 | 异常恢复 | 支持控制通道重连、任务重试、配置恢复和异常上报 | P0 |

| GW-015 | 审计日志 | 记录注册、审批、配置变更、密钥轮换、隔离和注销等事件 | P0 |
| GW-016 | 运行指标 | 采集节点资源、握手时间、流量、配置延迟和错误指标 | P0 |
| GW-017 | NAT 管理 | 按网络拓扑配置必要的 SNAT/DNAT 规则 | P1 |

P0 为首期必须实现；P1 可在核心功能稳定后分阶段实施。安全注册、访问控制、配置实际状态核验和节点撤销不得因分阶段交付而省略。

### 2.3 管理操作需求

管理能力最终应允许授权管理员：

- 查看节点 ID、名称、类型、网络区域、Agent 版本和生命周期状态。
- 生成、撤销注册凭证并审批注册申请。
- 查看节点公钥指纹、允许网段、Peer、路由及当前配置摘要。
- 查看控制通道、WireGuard 隧道和业务健康状态。
- 查看最近一次成功同步时间、配置失败阶段和错误原因。
- 触发重新同步、密钥轮换、隔离、停用和注销。
- 查询与节点有关的操作审计和安全事件。

控制台不得提供读取网关私钥的功能，也不得通过一个不受审计的管理入口直接将网关配置为无限制转发。

### 2.4 状态模型

生命周期状态、控制通道状态、隧道状态和业务健康状态必须分别维护。

| 状态维度 | 状态 | 说明 |
|---|---|---|
| 生命周期 | 待注册 | 管理端已创建逻辑节点，Agent 尚未完成注册 |
| 生命周期 | 待审批 | 注册请求已通过基础校验，等待审批 |
| 生命周期 | 配置中 | 已获准注册，正在生成和应用网络配置 |
| 生命周期 | 运行中 | 节点已激活，允许在有效授权范围内承载流量 |
| 生命周期 | 已隔离 | 节点存在安全或运维风险，已限制访问能力 |
| 生命周期 | 已停用 | 管理员主动停用，不能继续承载新访问 |
| 生命周期 | 已注销 | 节点身份和注册资格已撤销 |
| 控制通道 | 已连接/断开 | Agent 与控制面管理通道状态 |
| 隧道 | 正常/异常/未建立 | WireGuard 接口与 Peer 状态 |
| 业务健康 | 正常/降级/不可用 | 路由、过滤规则和目标资源的综合健康状态 |

控制通道断开不等同于节点注销；控制通道正常也不代表隧道或业务资源一定可用。离线期间是否允许继续转发已授权流量，应由企业安全策略明确规定。

## 三、网关核心基础能力实现

本阶段不依赖管理控制台。开发人员通过本地配置文件、命令行工具、单元测试、集成测试或模拟控制面验证网关的独立能力。

### 3.1 Gateway Agent 运行架构

建议使用 Go 实现常驻进程，并按职责划分内部模块：

| 模块 | 职责 |
|---|---|
| Agent 主进程 | 启动管理、生命周期、组件协调、退出处理 |
| 本地配置模块 | 读取配置、校验参数、管理当前配置摘要和本地状态 |
| 身份与密钥模块 | 生成唯一的 WireGuard 节点密钥、保护密钥材料、维护密钥状态 |
| 网络执行模块 | 管理 WireGuard、路由、ACL、防火墙和 NAT |
| 配置执行模块 | 接收配置对象、核验摘要与目标、执行变更、核验和回滚 |
| 健康检查模块 | 检查进程、控制通道、隧道、规则和资源连通性 |
| 监控审计模块 | 结构化日志、运行指标、事件和错误记录 |
| 控制通道模块 | 在后续阶段接入控制面，负责认证、心跳、配置接收和状态上报 |

各模块通过内部接口协作。网络执行模块只能执行经过验证的结构化操作，不应接收并执行来自远端的任意 Shell 字符串。

### 3.2 技术选型

| 技术领域 | 推荐方案 | 用途 |
|---|---|---|
| 核心开发 | Go | Agent、控制面服务和任务执行器 |
| 隧道 | Linux 内核 WireGuard；能力不可用时使用 WireGuard-Go 用户态设备 | 加密网络通道 |
| WireGuard 管理 | `wgctrl` 与 WireGuard-Go UAPI | 配置接口、Peer、AllowedIPs 和监听端口 |
| Linux 网络管理 | `vishvananda/netlink` | 管理隧道地址、接口状态和路由 |
| 防火墙与 NAT | `google/nftables` Netlink API；Docker 共存使用 `coreos/go-iptables` | 管理专属 nftables 表、转发 ACL、前缀 DNAT、受限范围的固定地址 SNAT；检测到 Docker 转发链时，将相同授权规则接入 `DOCKER-USER` |
| 控制通道 | HTTPS/gRPC + TLS | 后续与控制面通信 |
| 本地状态 | 权限受控的文件或本地状态存储 | 保存身份材料引用、当前配置摘要和恢复元数据 |
| 日志与指标 | 结构化日志、Prometheus 兼容指标或企业现有监控 | 运行监控和故障排查 |

具体库与操作系统版本应在目标部署环境中验证。首期应优先支持明确选定的 Linux 发行版与版本范围，避免一开始就承诺未经测试的跨平台能力。

当前 Gateway Agent 的 Linux 驱动使用 Go Netlink API 管理 WireGuard、路由和 nftables，不通过拼接 Shell 命令调用 `wg`、`ip` 或 `nft`。Docker 共存部分通过 `coreos/go-iptables` 对参数化的 `iptables`/`ip6tables` 规则进行管理，不使用 Shell 字符串。内核后端仅在 WireGuard 链路类型或 Generic Netlink 能力明确不可用时回退到用户态；权限错误、密钥错误、接口冲突和普通配置错误不会触发回退。VeloTrust ACL 使用专属 nftables 表，规则只匹配受管隧道接口；检测到 Docker 的 iptables 转发链时，还会将允许规则镜像到受管的 `VTGW-*` 链并接入 `DOCKER-USER`，保留已有拒绝规则和 Docker 的 `FORWARD` 策略。目标系统须提供 Linux nftables/Netlink 支持、创建 TUN/WireGuard 接口和写入转发 sysctl 所需权限；Docker 共存还要求 Docker 的 iptables 链和 Agent 使用相同的 iptables 前端；用户态回退还需要可用的 `/dev/net/tun`。

当前固定的直接依赖为 `github.com/coreos/go-iptables v0.8.0`（Apache-2.0）、`github.com/google/nftables v0.3.0`（Apache-2.0）、`github.com/vishvananda/netlink v1.3.1`（MIT）、`golang.zx2c4.com/wireguard v0.0.0-20231211153847-12269c276173`（MIT）和 `golang.zx2c4.com/wireguard/wgctrl v0.0.0-20241231184526-a9ab2273dd10`（MIT）。复用的是这些项目公开的库 API；没有引入其他控制服务、数据库实体或控制面业务模型。

WireGuard 接口生命周期、Peer 配置和 Linux 网络模块边界参考仓库提供的 `netbird-0.80.0.zip`（版本 `v0.80.0`，commit `fca64287cf51a85552a41b022013abbfdb335452`）；本轮 Gateway Agent 驱动由 VeloTrust 自行实现，不直接导入该项目的 Agent、管理服务或策略业务包。此前已经适配的通用网络辅助文件及来源记录见 [复用清单](netbird-reuse-manifest.md)。

### 3.3 Agent 启动流程

1. 读取本地配置并校验必填字段。
2. 检查运行权限、操作系统能力、WireGuard 支持和必要网络工具。
3. 加载本地 WireGuard 节点密钥；首次部署时按安全规则生成。
4. 初始化日志、监控和本地状态。
5. 检查当前配置内容摘要及本地网络状态。
6. 根据当前有效配置初始化 WireGuard、路由和访问规则。
7. 执行本地健康检查。
8. 进入运行循环，监听配置变更、健康检查和退出信号。

如果关键安全配置无效，Agent 不应通过放宽 ACL 的方式“尽量启动”。应进入受限状态，保留故障原因并等待安全恢复。

### 3.4 本地配置与命令行

在控制面集成前，建议提供受保护的本地配置文件和命令行管理能力。命令行至少支持：

- 检查配置合法性。
- 查看 Agent 版本和运行状态。
- 查看当前配置摘要和最后一次应用结果。
- 执行只读健康检查。
- 导出不包含秘密信息的诊断信息。
- 在受控条件下加载测试配置或触发配置核验。

本地管理接口应限制操作系统用户权限。对路由、WireGuard 和防火墙有修改能力的操作应有明确的权限边界与审计记录。

### 3.5 本地密钥生成与保护

每个节点只生成一个长期密钥对：WireGuard 密钥对。WireGuard 公钥既是 Peer 标识，也是控制面节点记录关联的网络公钥；私钥只在节点本地使用。它不能用于 Ed25519 签名或直接替代控制通道认证。

- 首次注册时，控制面通过一次性注册凭证或其他受信认证方式验证节点，并将该节点记录绑定到其 WireGuard 公钥。
- 控制面只保存公钥和必要元数据，不接收 WireGuard 私钥；节点只接受由可信控制面认证的配置。
- 在当前静态配置阶段，管理员手动配置双方公钥是唯一信任来源；尚未实现在线注册或控制面认证。
- 私钥文件必须限制所有者、权限和读取范围；日志、诊断包和普通配置导出不得包含私钥。
- 密钥轮换应有明确状态、验证步骤和旧公钥撤销流程。控制通道若需要会话凭证，应采用可撤销的短期凭证，不再为节点额外生成长期身份密钥对。

如部署环境具备 TPM、HSM 或系统密钥设施，可作为增强保护方案；不能将其视为所有首期部署都已具备的前提。

### 3.6 WireGuard 接口与 Peer 管理

网关需要实现：

1. 接口初始化：检查接口名称、隧道地址、监听端口和 MTU。
2. Peer 添加与更新：按配置更新公钥、Endpoint、AllowedIPs 和保活参数。
3. Peer 删除：删除不再授权或已撤销的对端。
4. 状态读取：采集最近握手时间和必要的收发统计。
5. 配置核验：将实际接口与 Peer 状态和期望配置进行比较。
6. 异常处理：对失败的更新返回明确错误，避免只记录命令退出码。
7. 密钥更新：在控制面协同下更新公钥，并验证新连接后撤销旧配置。

`AllowedIPs` 参与 WireGuard 的路由选择和来源地址约束，但不能单独替代业务访问授权。对于访问企业资源的网关，还必须由 ACL/防火墙落实资源级访问限制。

### 3.7 路由与流量转发

网关应只创建经过校验的路由，并具备路由冲突检测与实际状态核验能力。

- 对隧道地址池、企业网段和本机网段进行 CIDR 重叠检查。
- 校验目标网段、下一跳、路由表及路由优先级。
- 禁止未授权的任意网段宣告。
- 对新增路由检查返回路径，避免只配置单向路径。
- 路由删除时同步检查相关 Peer、ACL 和 NAT 规则。
- 多网关部署时明确路由优先级与切换策略。

网关只有在目标流量满足当前 ACL 和路由条件时才能转发。路由存在本身不代表授权。

### 3.8 ACL、防火墙与默认拒绝

访问过滤应以默认拒绝为基础：

- 明确允许的来源、目标资源、协议和端口。
- 对不同网络区域设置必要的隔离规则。
- 为规则记录来源策略标识、当前授权状态和关联授权。
- 更新规则时避免出现短暂的全放通窗口。
- 对规则应用结果进行实际核验。
- 撤销授权时清理相关规则；如安全要求立即切断已有连接，还需处理连接跟踪状态。
- 如果 ACL 无法安全应用，不得将节点标记为正常承载状态。

不能只增加“允许规则”而不考虑操作系统既有防火墙策略和默认动作，否则可能出现未授权流量绕过预期边界的情况。

### 3.9 NAT

NAT 仅在网络拓扑确有需要时启用，例如目标网络无法配置回程路由或企业网络明确要求源地址转换。

配置必须明确 NAT 类型、转换前后地址、适用接口、源/目标范围和授权边界。不得通过大范围 SNAT 掩盖路由设计问题，也不得因启用 NAT 而绕过访问控制。应用后应分别验证请求方向和返回方向的流量。

当前 Linux Agent 的 SNAT 仅接受固定单地址转换：配置隧道源前缀、目标前缀、出口接口和转换地址；转换地址必须已配置在该接口上。规则只匹配从受管隧道进入、并从指定接口发出的流量。转发 ACL 在 postrouting SNAT 之前匹配原始客户端地址，因此 NAT 本身不会授予访问权限。动态接口地址的 MASQUERADE 尚未实现。

### 3.10 配置执行、幂等与回滚

配置执行模块需要实现以下能力：

- 配置目标节点校验。
- 配置摘要校验；任务摘要与数据库当前摘要不一致时拒绝过期任务。
- 配置结构、CIDR、Peer、路由和规则冲突检查。
- 变更前预检查。
- 按依赖关系执行变更。
- 读取操作系统真实状态进行核验。
- 记录每一步的执行结果。
- 失败时恢复到最后一个已验证且仍符合当前授权的安全状态。

相同配置重复执行应是幂等的，不得重复添加路由或防火墙规则。回滚时必须重新检查授权是否仍然有效，不能恢复已撤销的访问权限。

### 3.11 本阶段完成标准

- Agent 可独立安装、启动、停止和重启。
- 能安全生成和保存唯一的本地 WireGuard 节点密钥。
- 能通过本地测试配置建立 WireGuard 接口和 Peer。
- 能管理路由、ACL、防火墙以及必要的 NAT。
- 能区分期望配置和实际配置，并报告应用结果。
- 能在无效配置或规则应用失败时保持安全状态。
- 能输出不含秘密信息的诊断结果。
- 核心网络操作不依赖管理控制台。

### 3.12 当前代码实现状态

仓库中的首个 Gateway Agent 数据面实现已覆盖以下部分：

- `gateway-agent keygen --dir` 只生成一对 WireGuard 节点密钥，将私钥保存为目录权限 `0700`、文件权限 `0600` 的文件，且不会覆盖已有密钥。WireGuard 公钥同时作为节点的网络身份标识和隧道 Peer 标识。配置可通过同目录的 `tunnel.private_key_file` 引用私钥；加载器会校验密钥文件权限，并将其内容纳入热重载指纹。`gateway-agent validate --config` 对本地私密配置进行严格校验；`gateway-agent run --config` 启动常驻进程，首次应用完整配置、每 2 秒检查本地配置文件并提供 `/healthz` 与 `/readyz`。发现配置文件损坏或不可读时立即 fail-closed；修复并提供有效配置后自动恢复。运维应以原子替换方式发布新配置。旧版本生成的 `node-identity.*` 文件不再使用，升级时不会自动删除。
- Linux WireGuard 优先使用内核接口和 `wgctrl`；检测到内核能力不可用时创建 WireGuard-Go 用户态设备。其他初始化错误保持失败并触发 fail-closed 清理。
- 路由通过 netlink 替换为完整目标集合，仅清理绑定到受管隧道且标记为本 Agent 管理协议号的路由。部署前须确保自有路由管理程序不使用协议号 253。
- ACL 在专属 nftables 转发链中按优先级匹配来源、目标、协议和端口。空规则集合默认拒绝；只允许从隧道进入且符合规则的连接，返回流量还须处于已建立/相关状态并匹配当前允许规则的反向地址、协议和服务端口，已撤销的授权不能依靠旧连接继续返回。检测到 Docker 的 iptables 转发链时，Agent 会将允许规则镜像到自有 `VTGW-*` 链并接入 `DOCKER-USER`，使 Docker 的 `FORWARD` 默认丢弃策略能放行同一批已授权流量；Agent 每 15 秒重查该挂接，以覆盖 Docker 重建链的情况；不改写 Docker 的全局策略或现有拒绝规则。
- NAT 使用 nftables 前缀 DNAT，将从隧道进入的目标影子前缀映射到真实前缀；也支持限定隧道来源、目标前缀和出口接口的固定地址 SNAT。转发 ACL 匹配 DNAT 后的目标地址和 SNAT 前的来源地址，因此 DNAT ACL 目标应使用真实资源网段，SNAT ACL 来源应使用客户端原始地址。
- Agent 在应用变更前阻断隧道转发；只有隧道、防火墙、路由、NAT 和转发开关全部应用成功后才解除阻断。正常退出会阻断流量、删除受管隧道和路由，并恢复本进程修改过的转发 sysctl 值。

本次实现仍使用本地单份期望配置，尚无节点注册、身份认证控制通道、在线配置同步或配置租约。配置文件热重载已支持完整代际替换；配置文件不合法或读取失败时会 fail-closed，修正后可自动恢复。进程被强制终止时，内核 WireGuard 接口、最后一次成功的 nftables 规则及 Docker `DOCKER-USER` 中的镜像规则可能暂时保留，直到服务重启或运维清理；需要依赖受控的服务自动重启和后续控制面配置租约实现更严格的崩溃收敛。当前自动化验证覆盖配置、策略表达式、回退边界和 Agent 生命周期；特权 Linux 网络集成须在具备 `CAP_NET_ADMIN`、TUN 和 nftables 内核支持的测试主机验证，未完成前不视为生产环境验收通过。

## 四、节点注册与身份认证机制

本阶段实现节点的可信注册和生命周期管理。可以先通过独立 API 或模拟控制面验证，不要求管理控制台已经完成。

### 4.1 管理员预创建节点

注册前应先创建逻辑网关记录，至少包含：

- 不可变的 `gateway_id`。
- 网关名称和类型。
- 计划所属的企业网络或网络区域。
- 允许申请的网段与能力范围。
- 注册是否需要审批。
- Agent 允许版本范围。
- 注册凭证有效期和使用次数。
- 生命周期初始状态。

预创建节点仅代表控制面存在一条逻辑记录，不代表真实服务器已注册或已获得访问权限。

### 4.2 注册凭证设计

建议建立独立的注册凭证数据实体。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | uint64/UUID | 凭证记录 ID |
| `gateway_id` | uint64/UUID | 绑定的网关节点 |
| `token_hash` | string | 注册凭证摘要，不保存明文 |
| `status` | string | 有效、已使用、已过期或已撤销 |
| `expires_at` | datetime | 过期时间 |
| `max_uses` | integer | 最大成功使用次数 |
| `used_count` | integer | 已使用次数 |
| `created_by` | uint64/UUID | 创建者 |
| `created_at` | datetime | 创建时间 |
| `revoked_at` | datetime/null | 撤销时间 |

凭证必须具备高强度随机性、有效期、使用次数限制、节点绑定和主动撤销能力。凭证消费需要事务或原子操作，防止并发请求重复使用。注册凭证只用于首次注册，不作为长期运行身份。

### 4.3 注册请求

Agent 提交的注册信息可以包含：

- `gateway_id` 和一次性注册凭证。
- 节点身份公钥和 WireGuard 公钥。
- Agent 版本、操作系统和 CPU 架构。
- 必要的网络能力声明和候选 Endpoint。
- 本地预检查结果。
- 防重放所需的请求 ID、随机数或时间信息。

不得提交私钥。控制面不能信任请求体自行声明的节点 ID，而应通过注册凭证绑定关系确认目标节点。

### 4.4 注册校验流程

1. 校验请求格式、大小和频率。
2. 根据凭证摘要查找注册凭证。
3. 校验凭证有效期、撤销状态、使用次数及绑定节点。
4. 校验节点是否存在且处于允许注册的状态。
5. 检查身份公钥和 WireGuard 公钥格式及冲突。
6. 校验请求防重放信息。
7. 原子地占用或消费注册凭证，并创建注册申请。
8. 根据审批规则进入“待审批”或“待配置”状态。
9. 记录审计事件并返回结果。

基础注册校验通过不等于节点已获准承载业务流量。需要人工审批的节点必须保持受限状态，直到审批完成并通过配置及健康检查。

### 4.5 审批、激活与身份认证

审批通过后，控制面将节点置于配置阶段，分配隧道地址并生成期望配置。Agent 使用长期节点身份凭证进行后续控制通道认证，建议采用双向 TLS 或基于节点私钥的请求签名方案。

长期身份机制必须支持：

- 节点 ID 与公钥/证书强绑定。
- 服务端身份验证。
- 凭证有效期、轮换和撤销。
- 请求防重放。
- 失效节点拒绝认证。
- 身份操作审计。

节点注册流程与 WireGuard 握手应分别验证。WireGuard 握手成功不能证明节点当前仍具有控制面权限。

### 4.6 节点隔离、停用和注销

节点隔离或注销时应执行完整撤销流程：

1. 控制面标记节点隔离或注销，拒绝新的控制请求。
2. 撤销节点身份凭证或将其列入拒绝列表。
3. 删除或禁用相关 WireGuard Peer。
4. 清理相关路由、ACL 和 NAT 规则。
5. 按安全要求清理已有连接跟踪状态。
6. 网关执行结果和控制面期望状态进行核对。
7. 记录成功、失败和仍待处理的任务。

如果网关已离线，控制面应保留待执行撤销任务，并确保节点重新连接时不能恢复已失效的配置。

### 4.7 本阶段完成标准

- 注册凭证限时、限次且可撤销。
- 节点身份与公钥绑定明确。
- 未审批节点不能承载业务流量。
- 长期认证不依赖首次注册凭证。
- 支持身份轮换、隔离和注销。
- 注册和身份失败均可审计、可定位。

## 五、配置同步与安全策略执行

### 5.1 期望状态与实际状态

控制面维护数据库中的当前期望配置；Agent 维护实际执行结果。配置任务需要跟踪当前期望内容到节点实际生效的完整过程。

建议每个配置任务包含：

- 任务 ID、目标网关 ID。
- 目标配置摘要；不携带递增的配置版本号。
- 变更类型及创建时间。
- 执行阶段、重试次数和最后执行时间。
- 网关报告的实际配置摘要。
- 失败步骤、错误码和诊断信息。

任务状态可以包括：待下发、已下发、执行中、成功、失败、待重试和已取消。

### 5.2 配置分发流程

1. 控制面根据当前网络拓扑和有效授权生成配置。
2. 对当前配置内容计算摘要并生成完整性校验信息。
3. 通过认证控制通道下发配置。
4. Agent 校验节点绑定、配置摘要、完整性和配置合法性；任务摘要已不等于控制面当前摘要时拒绝执行。
5. Agent 执行预检查并按依赖顺序应用配置。
6. Agent 核验 WireGuard、路由和防火墙的实际状态。
7. Agent 返回实际生效摘要、执行结果和失败原因。
8. 控制面更新状态；未成功的任务进入重试、修复或人工处理流程。

### 5.3 摘要与重试规则

- 不接受目标节点不匹配的配置。
- 不允许任务携带的旧配置覆盖数据库当前配置。
- 相同摘要的重复执行必须幂等。
- 重试采用退避机制并限制频率。
- 重连后优先获取当前有效配置，而不是无条件恢复本地旧配置。
- 配置重试前重新确认授权仍然有效。
- 实际状态与期望状态持续不一致时，应告警并按策略修复或隔离。

### 5.4 访问授权的落实与撤销

控制面计算用户、设备、资源、协议端口和有效期等条件后，将与网关有关的授权转化为数据面规则。网关应执行明确的 ACL 和必要路由，不应仅凭用户已登录或 Peer 已存在就开放整个网段。

撤销时应：

1. 更新数据库中的当前授权状态和期望配置摘要。
2. 阻止新增授权流量。
3. 删除相关 ACL、Peer 或路由。
4. 按要求清理已有连接。
5. 核验实际规则。
6. 向控制面报告撤销结果。

### 5.5 控制通道断连策略

控制面暂时不可达时，Agent 应按明确的企业策略运行：

- **受控离线模式：** 仅在本地配置完整、授权仍在有效期内且节点未收到撤销信号的条件下，允许有限流量继续运行。
- **严格在线模式：** 当无法在规定时间内确认授权状态时，阻断需要在线确认的访问。

具体策略由企业部署配置决定。Agent 不得因为控制面连接失败而自动切换到更宽松的访问模式。节点恢复连接后必须重新认证、获取当前有效配置并进行状态对账。

### 5.6 本阶段完成标准

- 配置任务可追踪到目标配置摘要和节点。
- 配置下发与实际生效状态能够区分。
- 失败重试不会扩大访问权限。
- 节点重启或控制通道恢复后能同步最新有效配置。
- 授权撤销能够落实到数据面并验证。
- 长期不一致或安全规则应用失败能够告警。

## 六、独立测试与生产加固

### 6.1 测试环境

在控制台集成前，建议准备最小独立测试环境：

- 一套控制面测试服务或模拟控制面。
- 一台网关测试服务器。
- 至少一台终端测试设备。
- 一台可访问和一台不可访问的测试资源。
- 明确规划的 WireGuard 隧道地址和企业测试网段。
- 可重复执行的路由、ACL、配置变更与故障注入脚本。

测试环境应与生产网络隔离，避免路由和防火墙测试影响企业现网。

### 6.2 功能测试

- Agent 安装、启动、停止、重启和配置加载。
- 节点密钥生成、文件权限和密钥轮换。
- WireGuard 接口及 Peer 的创建、更新和删除。
- 隧道地址、CIDR 冲突和路由优先级校验。
- ACL 创建、更新、撤销和默认拒绝。
- 配置摘要、重复任务和幂等执行。
- 配置部分失败、回滚和重新同步。
- 节点隔离、注销及重新注册。
- 控制面断连与恢复后的状态对账。

### 6.3 网络与授权测试

- 已授权终端访问指定资源成功。
- 未授权终端不能访问受保护资源。
- 已授权用户访问未授权端口被拒绝。
- 不同安全域之间的访问受规则约束。
- 路由存在但 ACL 未授权时，流量仍被阻断。
- WireGuard 正常但目标服务不可达时，系统能识别为业务可达性问题。
- 撤销授权后新增访问被阻断。
- 根据安全要求验证已有连接是否被清理。

### 6.4 异常与安全测试

| 场景 | 预期行为 |
|---|---|
| 注册凭证过期 | 拒绝注册并记录原因 |
| 同一凭证并发提交 | 不允许多次成功消费 |
| 未审批节点尝试访问 | 不得承载业务流量 |
| 公钥与现有节点冲突 | 拒绝或进入人工核查，不覆盖原身份 |
| 收到与数据库当前摘要不符的配置 | 拒绝应用并重新获取当前配置 |
| ACL 应用失败 | 不得将节点报告为完全健康 |
| 控制面不可达 | 按既定离线策略运行，不扩大权限 |
| Agent 异常退出 | 恢复后重新认证并对账 |
| 节点身份被撤销 | 拒绝后续控制认证并触发数据面撤销 |
| 非法路由配置 | 拒绝应用并保持安全状态 |
| 诊断日志导出 | 不得包含私钥、注册凭证明文等秘密 |

### 6.5 性能与容量测试

性能指标需要结合目标服务器规格和实际企业网络规模压测后确定，不应在没有测试数据的情况下承诺固定数值。测试至少覆盖：

- 不同 Peer 数量下的内存和 CPU 使用情况。
- 不同流量规模下的吞吐量、时延和丢包率。
- 大量配置更新时的应用耗时和失败率。
- 配置任务积压、重试和控制面恢复时的收敛时间。
- 多条 ACL 规则下的转发性能。
- 长时间运行、日志增长和异常重启恢复。

### 6.6 监控与日志

建议采集以下指标：

- Agent 运行状态、进程重启次数和系统资源。
- 控制通道最近成功连接时间。
- 当前配置摘要、实际生效摘要和配置应用耗时。
- WireGuard Peer 数量、最近握手时间及流量统计。
- 路由和防火墙规则应用失败次数。
- 目标资源探测结果。
- 待处理配置任务数量和重试次数。

审计应覆盖注册、审批、身份变更、配置应用、密钥轮换、隔离、注销和管理员操作。默认不记录业务载荷、密码、注册凭证明文或私钥。

### 6.7 故障恢复要求

| 故障 | 处理策略 |
|---|---|
| 控制面暂时不可达 | 退避重连，遵循已配置的离线策略 |
| WireGuard 握手失败 | 检查 Endpoint、公钥、UDP 可达性和 Peer 配置 |
| 路由冲突 | 拒绝变更并保留已验证的安全配置 |
| ACL 应用失败 | 不放开访问，报告失败并修复或回滚 |
| 目标资源不可达 | 分别检查路由、ACL、NAT、回程路径和目标服务 |
| Agent 重启 | 加载受保护状态，重新认证并同步当前有效配置 |
| 节点撤销但已离线 | 保留撤销任务，重连后禁止恢复过期授权 |
| 配置长期不一致 | 告警，触发修复或按安全策略隔离 |

### 6.8 本阶段完成标准

- 核心功能、网络隔离和撤销流程通过测试。
- 配置失败不会导致默认放通。
- Agent 重启和控制面恢复后能够安全收敛。
- 指标和审计足以定位常见故障。
- 完成目标部署环境的性能与稳定性测试。
- 已知限制、运维手册和故障处理步骤形成文档。

## 七、核心数据模型设计

以下为控制面逻辑数据模型建议，不限定具体 ORM。数据模型应保持网关身份、运行状态、当前配置摘要和审计事件之间的职责分离。

### 7.1 `gateway_node` 网关节点

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | uint64/UUID | 主键及不可变节点标识 |
| `gateway_name` | varchar(128) | 网关名称 |
| `gateway_type` | varchar(32) | 网关类型 |
| `status` | varchar(32) | 生命周期状态 |
| `network_id` | uint64/UUID | 关联企业网络或网络区域 |
| `wireguard_public_key` | varchar(128) | 节点唯一公钥，同时用于节点网络身份关联和 WireGuard Peer 验证 |
| `agent_version` | varchar(64) | 当前 Agent 版本 |
| `config_hash` | varchar(128) | 数据库当前期望配置的内容摘要 |
| `applied_config_hash` | varchar(128) | 网关已确认应用的内容摘要；未知时为空 |
| `last_seen_at` | datetime | 最近有效心跳时间 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |
| `revoked_at` | datetime/null | 撤销时间 |

### 7.2 其他实体

| 实体 | 用途 |
|---|---|
| `gateway_registration_token` | 注册凭证摘要、有效期、次数和撤销状态 |
| `gateway_key_record` | 身份公钥、WireGuard 公钥、密钥用途、版本及轮换状态 |
| `gateway_config` | 每个目标唯一的当前配置、内容摘要和配置元数据 |
| `gateway_config_task` | 配置下发、应用、重试和失败追踪 |
| `gateway_peer` | 网关与终端或其他网关的 Peer 关系 |
| `gateway_health_status` | 控制通道、隧道和业务健康状态 |
| `gateway_audit_log` | 注册、审批、配置、密钥、隔离和注销事件 |

私钥不应以普通数据库字段的形式直接存储。运行指标、审计事件和生命周期状态建议分别管理，避免用一个状态字段覆盖所有运行信息。

## 八、独立接口与控制面契约

虽然管理控制台集成放在最后，但核心开发开始前应定义稳定的接口契约。接口契约用于解耦模块，不意味着必须先完成控制台页面。

### 8.1 逻辑接口

| 接口 | 方法 | 用途 |
|---|---|---|
| `/api/v1/gateways/registrations` | POST | 提交注册请求 |
| `/api/v1/gateways/registrations/{id}/approve` | POST | 审批注册请求 |
| `/api/v1/gateways/{id}/bootstrap` | POST | 获取首次激活所需的有限配置 |
| `/api/v1/gateways/{id}/config` | GET | 获取当前有效配置 |
| `/api/v1/gateways/{id}/config-ack` | POST | 上报配置应用结果 |
| `/api/v1/gateways/{id}/heartbeat` | POST | 上报运行状态 |
| `/api/v1/gateways/{id}/health` | POST | 上报健康检查结果 |
| `/api/v1/gateways/{id}/keys/rotate` | POST | 触发密钥轮换流程 |
| `/api/v1/gateways/{id}/isolate` | POST | 执行节点隔离 |
| `/api/v1/gateways/{id}/revoke` | POST | 撤销节点身份与注册资格 |

上述路径为逻辑示例，最终应结合控制面 API 规范统一。Agent 侧的本地命令行和配置执行接口应与远程控制 API 分开，避免远程请求直接触发任意本机命令。

### 8.2 三类必须提前确定的契约

1. **节点身份契约：** `gateway_id`、唯一的 WireGuard 公钥、注册凭证、注册状态、隔离和注销语义。
2. **网络配置契约：** Peer、隧道地址、Endpoint、AllowedIPs、路由、ACL、NAT、配置摘要和完整性信息。
3. **运行状态契约：** 生命周期状态、控制通道状态、隧道状态、业务健康状态、配置应用结果和错误码。

接口应包含幂等语义、错误码、版本兼容规则和审计关联 ID。控制面不应依赖 Agent 的内部类名或本地实现细节。

## 九、最后阶段：与控制面和管理控制台集成

本阶段在网关独立功能、注册机制、配置同步和测试加固完成后实施。此前各阶段使用本地配置、命令行、模拟控制面或独立 API 验证，不以控制台页面是否完成作为网关核心功能的前置条件。

### 9.1 集成目标

- 接入正式的网关注册、身份认证和审批服务。
- 接入正式的网络编排、策略计算和配置分发服务。
- 将网关运行状态、期望/实际配置摘要、隧道状态和健康结果展示到管理控制台。
- 支持通过控制台执行注册审批、重新同步、密钥轮换、隔离和注销。
- 完成管理操作、配置任务和节点状态的端到端审计。

### 9.2 集成顺序

1. **控制面 API 对接：** 使用已经确定的身份、配置和状态契约替换模拟控制面。
2. **注册链路联调：** 验证预创建节点、注册凭证、审批、激活和身份认证。
3. **配置链路联调：** 验证控制面生成配置、Agent 应用、实际状态核验和配置确认。
4. **状态与审计联调：** 验证心跳、健康状态、错误信息、配置任务及审计事件。
5. **控制台管理操作：** 接入注册审批、重新同步、密钥轮换、隔离、停用和注销等操作。
6. **端到端验收：** 从管理员创建网关开始，完整验证终端访问授权资源、撤销授权及节点故障恢复。

### 9.3 控制台功能需求

控制台至少应提供：

- 网关节点列表、详情、筛选和状态展示。
- 创建节点、生成注册凭证、撤销凭证。
- 注册申请审批与拒绝。
- 节点网络区域、允许网段及 Peer 关系查看。
- 期望配置摘要、实际生效摘要和最后同步时间展示。
- 控制通道、隧道和业务健康状态展示。
- 配置失败原因、错误阶段和重试入口。
- 密钥轮换、节点隔离、停用和注销操作。
- 操作审计与节点事件查询。

控制台只负责调用受授权的管理 API，不直接操作网关操作系统，也不读取节点私钥。危险操作应有权限校验、二次确认和审计记录。

### 9.4 集成验收标准

- 控制台创建的节点能按预期完成注册。
- 审批状态与节点真实可用状态一致。
- 配置下发成功后，控制台展示网关确认的实际配置摘要及其与数据库当前摘要的匹配状态。
- 配置失败时能够展示失败阶段和可操作的恢复方式。
- 控制台发起隔离或注销后，数据面最终落实相关撤销。
- 控制通道中断时，控制台不会误报网关业务完全健康。
- 所有管理操作都能追溯到操作者、时间、目标节点和执行结果。

## 十、实施阶段与交付物

| 阶段 | 工作重点 | 主要交付物 | 完成条件 |
|---|---|---|---|
| 第一阶段：网关核心基础能力 | Agent、密钥、WireGuard、路由、ACL、配置执行 | Gateway Agent、配置规范、本地 CLI、核心单元及集成测试 | 不依赖控制台即可完成基础网络操作和验证 |
| 第二阶段：客户端与网关网络互通 | 客户端到网关资源访问；网关间 Peer、站点路由和转发 | 本地配置互通样例、端到端网络测试 | 客户端可访问授权资源；网关间路由按策略转发且默认拒绝未授权流量 |
| 第三阶段：节点注册与身份 | 注册凭证、身份绑定、审批、激活、隔离和注销 | 注册接口、身份模型、凭证管理、状态机和测试 | 未授权节点不能激活，身份生命周期可控 |
| 第四阶段：配置同步与安全执行 | 配置摘要、确认、重试、对账和撤销 | 配置任务机制、配置 ACK、摘要对账、撤销流程 | 配置失败和授权撤销可安全收敛 |
| 第五阶段：独立测试与生产加固 | 网络、安全、稳定性、性能和监控 | 测试报告、监控指标、审计规范、运维手册 | 核心场景通过测试，已知限制明确 |
| 第六阶段：控制面与控制台集成 | 正式 API、页面、管理操作和端到端联调 | 集成实现、控制台页面、联调报告 | 从节点创建到业务访问及撤销的全流程通过验收 |

### 10.1 首期交付范围建议

先完成单网关、单企业部署下的客户端访问闭环，再扩展到网关间互通：

1. Agent 生成并保护本地密钥，使用本地配置建立 WireGuard 隧道和 Peer。
2. 客户端通过网关访问被授权的测试资源，并验证路由、ACL 和默认拒绝行为。
3. 扩展到网关间 Peer 和站点路由，验证双向访问与路由撤销。
4. 管理员预创建网关，使用一次性凭证完成注册和审批。
5. 配置确认、健康检查和状态上报能够反映实际应用状态。
6. 撤销授权或隔离节点后，实际 Peer、路由和防火墙规则生效。
7. Agent 重启或控制面断连后，能够按既定安全策略恢复。

NAT 复杂场景、多网关高可用、中继、自动升级等能力可以在核心闭环稳定后实施，但应保留必要的架构扩展点。

## 十一、最终设计结论

VeloTrust 网关节点应建设为具有独立身份、独立运行能力和明确安全边界的受管网络组件，而不是仅负责启动 WireGuard 的简单代理程序。

本方案采用“**核心数据面先行、网络互通验证、注册与配置机制、生产加固、控制台集成最后**”的实施顺序：

- 先完成 Agent、WireGuard、路由、ACL 和本地配置执行。
- 使用本地配置先打通客户端到网关的授权访问，再扩展到网关间互通。
- 网络互通路径验证后，实现可信注册、节点身份和生命周期管理。
- 随后完善当前配置摘要、应用确认、重试、状态对账和授权撤销。
- 在接入控制台之前，完成独立测试、故障恢复和安全验证。
- 最后对接正式控制面与管理控制台，完成端到端集成。

这一顺序能够减少前期对页面和接口联调的依赖，同时通过提前定义身份、配置和状态契约，降低后期集成返工风险。最终验收以实际网络行为、安全策略是否生效、配置状态是否可信及撤销是否完成为准，而不是仅以接口调用成功或隧道握手成功为准。
