# VeloTrust 客户端功能需求与技术详细实现方案（定稿）

- 文档版本：V1.0
- 适用产品：VeloTrust 企业级零信任安全访问平台（ZTNA）
- 适用部署：企业自托管、单企业部署
- 客户端定位：安装在员工或受管终端上的 VeloTrust Client / Endpoint Agent
- 核心技术方向：Go、WireGuard、HTTPS/gRPC、操作系统原生网络与安全能力
- 文档范围：客户端功能需求、独立运行架构、用户认证、设备注册、隧道连接、访问策略执行、配置同步、密钥保护、异常恢复、测试验收，以及最后阶段与控制面和管理控制台集成

---

## 一、文档目标与设计原则

### 1.1 文档目标

本文档定义 VeloTrust 客户端的业务功能、模块边界、关键技术、业务流程、安全约束、实施顺序和验收标准，为客户端 Agent、桌面交互界面、系统网络适配层及后续控制面集成提供统一依据。

VeloTrust 客户端不是一个单纯的 WireGuard 启动器，也不应仅作为登录页面的包装。它需要在终端上建立可验证的设备身份，完成用户身份认证，获取经过控制面授权的网络配置，安全地建立加密隧道，并在权限变化、设备失信或会话失效时及时停止或收缩访问能力。

客户端负责把控制面的可信决策落实到当前终端，但不拥有最终授权决策权。客户端可以执行本地安全检查、校验配置完整性、检测连接状态并阻止明显不安全的连接；访问权限的最终判断由控制面策略引擎完成，网络网关和服务端策略共同落实数据面限制。客户端本地显示“已连接”不能被解释为所有资源均可访问。

### 1.2 设计原则

1. **先独立实现，再集成控制台。** 客户端核心能力先通过本地配置、命令行、模拟控制面和自动化测试完成；管理控制台和最终产品交互集成放在最后阶段。
2. **身份认证与网络授权分离。** 用户登录成功只证明用户身份，不自动授予网络访问权限；设备注册成功也不代表设备永久可信。
3. **客户端身份与 WireGuard 密钥分离。** 客户端身份密钥用于设备证明、控制通道认证或请求签名；WireGuard 私钥只用于隧道，不得混用。
4. **最小权限与默认拒绝。** 未获得有效授权、配置不完整或配置签名/摘要校验失败时，不建立新的受保护访问路径；不能以“连接可用”为理由自动放宽路由或防火墙。
5. **控制面是授权事实来源。** 客户端不自行创造权限，不通过修改本地文件绕过服务端授权，也不把 UI 状态作为安全判断依据。
6. **配置摘要与实际状态分离。** 收到配置不代表配置已应用，发起连接不代表隧道已建立，隧道已建立也不代表目标资源可达。每一阶段都需要独立状态与可诊断结果。
7. **密钥与凭证可撤销。** 设备丢失、用户离职、会话撤销或客户端密钥泄露时，控制面应能够撤销身份和网络授权，客户端在重新联机时必须收敛到撤销后的状态。
8. **系统权限透明、操作可审计。** 客户端申请系统管理员权限时必须限定用途；网络配置变更、登录、连接、断开、配置失败和安全事件均应有结构化记录，但不得记录密码、令牌或私钥。
9. **平台能力分阶段承诺。** 首期明确支持的操作系统、版本、架构和网络场景；未经验证的平台不宣称完整支持。跨平台共用业务逻辑，操作系统网络操作通过独立适配层实现。
10. **面向企业自托管。** 不设计多租户选择、租户级策略或跨企业账号体系。客户端连接到企业管理员配置的 VeloTrust 实例，企业间隔离由独立部署边界保证。

### 1.3 术语说明

| 术语 | 说明 |
|---|---|
| VeloTrust Client | 面向终端用户的客户端产品，包括后台 Agent、网络执行组件和可选桌面 UI |
| Client Agent | 常驻后台进程，负责设备身份、控制通道、配置同步、WireGuard、网络状态和安全事件处理 |
| Desktop UI | 展示登录、连接、状态、诊断和用户可执行操作的图形界面；不直接持有高权限网络执行能力 |
| Device Identity | 设备身份密钥、设备凭证及控制面登记的设备记录 |
| Session | 用户完成认证后形成的有期限、可撤销的身份会话 |
| WireGuard Tunnel | 由 WireGuard 提供的加密网络通道 |
| 授权配置 | 控制面基于当前用户、设备、资源与策略计算并下发的配置集合 |
| 配置摘要 | 用于识别当前期望配置和实际应用内容的摘要；不递增、不保留历史配置 |
| 连接状态 | 客户端控制通道、隧道、路由及业务探测等多个维度的综合状态，不是单一布尔值 |
| 设备信任状态 | 由控制面管理的待审批、可信、受限、已撤销等设备状态 |

## 二、客户端功能需求

### 2.1 功能范围

客户端负责终端侧的用户认证交互、设备注册与身份维护、受保护凭证存储、控制面通信、配置接收与校验、WireGuard 隧道生命周期管理、路由/DNS 等网络配置协调、连接健康检测、访问状态展示、故障恢复和诊断信息收集。

客户端不负责创建企业策略、不自行批准设备、不替代控制面完成最终访问授权，也不直接管理企业网关的系统路由和防火墙。企业资源目录、策略引擎、节点编排及网关侧 ACL 由控制面和网关实现。

### 2.2 功能需求清单

| 编号 | 功能模块 | 功能需求 | 优先级 |
|---|---|---|---|
| CL-001 | 安装与启动 | 支持安装、升级、卸载、后台服务启动与退出 | P0 |
| CL-002 | 实例配置 | 支持配置企业自托管控制面地址，校验 HTTPS/TLS 和实例标识 | P0 |
| CL-003 | 用户认证 | 支持用户名密码或企业身份源认证，并预留 OIDC/SAML 等方式 | P0 |
| CL-004 | MFA | 根据控制面要求完成 TOTP、一次性验证码或外部身份源二次认证 | P0 |
| CL-005 | 会话管理 | 支持登录、续期、退出、过期处理和服务端撤销响应 | P0 |
| CL-006 | 设备身份 | 首次启动生成设备身份密钥，创建或恢复设备注册关系 | P0 |
| CL-007 | 设备审批 | 展示待审批、受限或撤销状态，不绕过控制面审批 | P0 |
| CL-008 | 密钥保护 | 使用操作系统安全存储或受限权限文件保存私钥和敏感凭证 | P0 |
| CL-009 | 配置同步 | 拉取/接收授权配置，校验签名、当前内容摘要、有效期和目标设备绑定 | P0 |
| CL-010 | WireGuard | 创建、启动、停止和查询隧道，维护 Peer 与接口状态 | P0 |
| CL-011 | 路由控制 | 仅应用控制面批准的路由，处理路由冲突并记录实际结果 | P0 |
| CL-012 | DNS 管理 | 按授权配置应用企业 DNS/域名解析策略，并在断开时恢复原状 | P0 |
| CL-013 | 访问范围 | 只对获准网段或资源建立访问路径，不擅自接管全局流量 | P0 |
| CL-014 | 连接状态 | 分别展示登录、控制通道、隧道、配置同步和资源探测状态 | P0 |
| CL-015 | 撤销与断开 | 处理用户退出、设备撤销、会话失效、策略收缩及紧急断开 | P0 |
| CL-016 | 故障恢复 | 支持网络切换、休眠唤醒、控制通道重连和安全重试 | P0 |
| CL-017 | 日志与诊断 | 提供不含秘密信息的诊断包、错误码和本地日志 | P0 |
| CL-018 | 自动启动 | 可配置系统启动后后台运行，但须明确用户可见状态 | P1 |
| CL-019 | 自动连接 | 支持按企业策略和用户设置自动连接，遵循认证与设备状态 | P1 |
| CL-020 | 终端合规 | 预留操作系统版本、客户端版本、磁盘加密或 EDR 状态检查接口 | P1 |
| CL-021 | 多网络环境适配 | 支持 Wi-Fi/有线切换、NAT 变化、休眠唤醒后的连接恢复 | P1 |
| CL-022 | 应用级访问 | 如后续需要，扩展到应用代理或按应用识别的访问控制 | P2 |

P0 为首期必须实现的安全和连接闭环；P1 在核心链路稳定后实施；P2 属于扩展能力，不应成为首期网络访问的隐含前提。首期建议先支持明确选定的桌面操作系统，具体平台与版本范围在实施计划中固定。

### 2.3 用户可见状态

客户端应将多个内部状态转换为明确、可理解的用户提示，避免单一“已连接”掩盖真实问题。

| 状态 | 用户可见说明 | 访问行为 |
|---|---|---|
| 未登录 | 尚未完成用户认证 | 不建立受保护隧道 |
| 正在认证 | 正在验证用户身份或执行 MFA | 不授予新的网络访问权限 |
| 待设备审批 | 设备已提交注册，等待管理员审批 | 不建立正式访问路径 |
| 正在获取配置 | 身份已验证，正在请求设备授权与网络配置 | 不使用旧的未确认授权扩展访问范围 |
| 正在连接 | 正在应用隧道和网络配置 | 仅在配置校验与必要检查通过后开放访问 |
| 已连接 | 控制面状态、隧道及本地配置达到已定义的健康条件 | 仅访问当前授权资源 |
| 部分可用 | 隧道已建立，但部分路由或资源探测失败 | 显示受影响范围，不宣称全部可用 |
| 连接异常 | 隧道、配置或控制通道存在异常 | 按策略保留、收缩或断开现有访问 |
| 授权已撤销 | 用户会话、设备或策略已失效 | 清除对应授权配置并停止访问 |
| 已断开 | 隧道已关闭，临时路由/DNS 已按策略清理 | 不通过 VeloTrust 隧道访问受保护资源 |

客户端不得只依据最近一次 WireGuard 握手就判断资源访问正常。健康判断至少应区分控制通道、配置同步、隧道、路由/DNS 应用和可选资源探测。

## 三、客户端总体架构与模块边界

### 3.1 架构组成

建议采用“低权限 UI + 后台 Agent + 平台网络适配层”的结构。后台 Agent 是客户端核心；桌面 UI 负责交互和状态展示；需要管理员权限的网络操作由受控的系统服务执行。

| 模块 | 主要职责 | 权限原则 |
|---|---|---|
| Desktop UI | 登录交互、连接/断开、状态展示、错误提示、诊断导出 | 尽量使用普通用户权限，不直接操作路由或读取私钥 |
| Local IPC | UI 与 Agent 之间的本地通信、请求校验和事件通知 | 仅允许当前用户或受授权用户访问；验证调用方身份 |
| Client Agent | 生命周期协调、身份与会话状态、控制通道、配置编排、健康检查 | 仅持有业务必需权限，不直接暴露任意命令执行接口 |
| Identity Manager | 设备密钥、设备凭证、会话引用、密钥轮换状态 | 敏感材料最小化读取，禁止写入普通日志 |
| Control Channel | 与控制面进行认证、配置获取、心跳、撤销通知和状态上报 | TLS 校验、请求认证、超时与重试控制 |
| Config Manager | 配置接收、摘要校验、差异计算和应用编排 | 只接受符合协议和设备绑定的结构化配置 |
| WireGuard Manager | 隧道接口、Peer、Endpoint、AllowedIPs 与连接状态 | 不接受远端任意 Shell 命令 |
| Network Adapter | 平台路由、DNS、代理/防火墙辅助配置和恢复 | 高权限操作白名单化、幂等化、可审计 |
| Health Monitor | 监控 Agent、控制通道、隧道、路由、DNS 和资源探测 | 只读检查优先，探测范围受控 |
| Update Manager | 版本检查、安装包签名校验、升级与失败恢复 | 只安装可信签名版本，避免远程执行未验证包 |
| Diagnostics | 结构化日志、错误码、脱敏诊断包 | 默认脱敏，不包含秘密材料及不必要的业务数据 |

### 3.2 进程与权限隔离

桌面 UI 与高权限 Agent 应分离，防止 UI 漏洞直接获得系统网络配置权限。二者通过本地 IPC 通信，可根据操作系统使用 Unix Domain Socket、命名管道或受访问控制的本地 RPC。

IPC 接口应采用固定方法集合，例如获取状态、请求登录、请求连接、请求断开、查询诊断和订阅状态变化。不得提供“执行任意命令”“传入任意可执行路径”或“传入任意路由命令”等通用高权限接口。

Agent 应校验 IPC 调用者身份、请求参数、调用频率及操作状态。连接和断开请求应幂等；敏感操作应产生审计事件。若 UI 与 Agent 版本不兼容，应返回明确的协议版本错误，而不是按不完整字段继续执行。

### 3.3 建议代码模块

可按以下包边界组织 Go 项目，具体目录名称可根据仓库规范调整：

```text
client/
  cmd/
    client-agent/          # 后台 Agent 入口
    client-cli/            # 开发与运维诊断命令
  internal/
    app/                   # 生命周期与状态机协调
    config/                # 本地配置、远端配置模型与校验
    identity/              # 设备身份、凭证引用与密钥轮换
    auth/                  # 用户登录、MFA、会话状态
    control/               # 控制面 API、长连接/轮询、重试
    tunnel/                # WireGuard 接口与 Peer 管理
    network/               # 路由、DNS、平台适配器
    policy/                # 本地策略约束与配置校验，不替代服务端授权
    health/                # 状态采集与连通性探测
    ipc/                   # UI 与 Agent 的本地通信
    update/                # 更新包校验和升级编排
    diagnostics/           # 日志脱敏、诊断包
    platform/               # Windows/macOS/Linux 平台实现
  api/                     # IPC 与控制面协议定义
  packaging/               # 安装包、服务配置、签名与升级脚本
  tests/                   # 单元、集成、平台和端到端测试
```

目录只是建议，关键是保持业务逻辑与操作系统细节分离。`network` 层通过接口暴露路由、DNS 和系统状态操作；各平台分别实现适配器，并由相同的业务测试验证行为一致性。

### 3.4 关键接口原则

- 网络操作使用结构化参数，不接受未经校验的字符串命令。
- 配置模型使用明确的 schema_version、字段校验和兼容性规则；schema_version 只标识数据结构，不是业务配置版本。
- 控制面协议与 UI IPC 协议分开演进，避免 UI 直接依赖内部控制面 API。
- 身份、会话、设备和隧道状态分开保存，避免一个 `connected=true` 字段代表所有状态。
- 所有耗时网络操作支持 context 取消、超时、幂等重试和可观察错误。
- 业务逻辑依赖抽象接口，便于使用模拟 WireGuard、模拟操作系统网络和模拟控制面进行独立测试。

## 四、安装、初始化与实例配置

### 4.1 安装与运行模式

客户端安装包负责安装后台 Agent、桌面 UI（如采用）、必要的 WireGuard 组件及系统服务定义。安装过程必须明确展示系统权限用途，不应静默安装不必要的驱动、证书或网络过滤组件。

首期应选定支持的平台及版本范围，并逐个平台验证安装、升级、卸载和系统重启后的行为。不同操作系统的网络能力差异应由平台适配层处理，不能仅凭 Go 代码可以编译就认定平台已受支持。

运行模式建议包括：

- **用户交互模式：** 用户主动登录、连接、断开并查看状态。
- **后台服务模式：** Agent 负责维持连接、刷新配置和处理撤销；是否允许在无用户登录时继续工作由企业策略决定。
- **诊断模式：** 只读检查版本、服务、配置校验、网络状态和错误记录，不默认执行高风险修复。

### 4.2 企业实例地址配置

客户端需要知道所属企业自托管控制面的入口地址。可通过安装参数、管理员分发配置或首次启动页面配置，不应默认依赖公共 SaaS 服务。

配置入口至少包含控制面 HTTPS 地址和必要的实例标识。客户端应拒绝不安全的明文 HTTP（仅可在明确隔离的开发测试环境通过单独开关启用），校验 TLS 证书链、主机名和有效期。不得为了解决证书错误而默认跳过 TLS 验证。

如需企业私有 CA，应提供受控的 CA 信任配置或采用系统信任存储；信任材料应有版本和更新机制。客户端不能让任意普通用户通过输入一个地址就将企业设备注册到未知控制面。生产环境可通过管理员预配置、签名配置文件或首次注册码绑定实例。

### 4.3 首次启动流程

1. 安装程序完成文件部署和服务注册，验证安装包来源与签名。
2. Agent 启动后读取本地实例配置并检查其合法性。
3. 若缺少实例配置，进入等待管理员配置状态，不创建未经绑定的网络连接。
4. 生成设备身份密钥；如平台提供安全硬件或密钥库，优先将私钥放入安全存储。
5. 生成设备注册请求所需的公钥、客户端版本、平台类型及最小必要设备元数据。
6. 等待用户认证和设备注册流程完成。
7. 注册通过后获取设备凭证及配置能力，仍需等待控制面下发有效授权配置后才能建立受保护访问。

### 4.4 本地配置文件

本地配置仅用于客户端运行参数和企业实例绑定，不应成为绕过控制面授权的第二套策略来源。配置中可包括控制面地址、日志级别、诊断开关、允许的平台功能和本地缓存路径；不得明文保存用户密码、长期访问令牌或私钥。

配置文件应有明确 schema 版本、字段白名单、默认值和校验规则。配置变更应通过原子写入或等效机制完成，防止进程中断时留下半写入文件。生产配置和测试配置应隔离，不能因调试参数而关闭证书校验或访问控制。

## 五、用户身份认证与会话管理

### 5.1 模块职责

客户端认证模块负责与控制面配合完成用户登录、MFA、会话续期、退出和认证状态展示。客户端不应在本地验证一份自行保存的用户名密码后就认为用户已通过企业认证；身份验证结果必须来自可信控制面或配置的企业身份源。

### 5.2 认证方式与协议边界

首期可按控制面已实现的能力支持用户名密码与 MFA，并将 OIDC 等企业单点登录作为可扩展认证方式。具体认证协议应由控制面统一定义，客户端避免自行实现密码存储、密码策略或外部身份断言校验。

对于基于浏览器的 OIDC 登录，优先使用系统浏览器与授权码 + PKCE 等适合原生客户端的流程。回调应采用经过验证的 loopback URI 或操作系统安全支持的应用链接；校验 `state`、`nonce` 和回调关联关系，避免登录 CSRF 与会话串用。客户端不应通过嵌入式 WebView 收集企业 IdP 密码，除非企业身份方案明确要求且已评估其安全性。

### 5.3 登录业务流程

1. 用户从 UI 发起登录，Agent 检查企业实例配置和本地设备状态。
2. 客户端向控制面获取登录流程信息，按服务端要求执行密码认证、浏览器 SSO 或其他认证方式。
3. 如需要 MFA，客户端展示服务端指定的验证步骤，并提交一次性验证结果。
4. 控制面验证身份、账户状态、认证强度和风险规则后签发短期访问凭证或建立会话。
5. 客户端只保存必要的会话凭证引用或受保护的刷新凭证，不在普通配置文件中保存秘密。
6. 登录成功后仍需检查设备是否已注册、审批和可信，并向控制面请求设备级授权配置。
7. 认证失败时展示可理解的错误信息，但不向 UI 暴露可被用于账户枚举的敏感细节。

### 5.4 会话续期与撤销

访问令牌应尽量短期化。若使用刷新令牌，必须保存在操作系统安全存储中，并按控制面要求轮换。刷新失败、会话撤销、用户停用或服务端返回需要重新认证时，客户端应清理本地会话状态，并按策略停止或收缩隧道访问。

客户端本地注销不等于服务端会话已经撤销。退出时应尝试通知控制面撤销会话，同时立即清理本地凭证引用并执行本地断开策略；若网络不可用，应记录待完成的注销动作并在下次联机时补交。不能因注销请求暂时失败而继续显示为已登录或无限期保留高权限访问。

### 5.5 用户认证与设备身份的关系

用户身份与设备身份是两个独立维度：用户登录证明“谁在使用”，设备凭证证明“哪台设备在连接”。控制面必须将二者关联后再评估授权。用户退出后，设备记录可以继续存在，但用户会话对应的访问授权应按策略终止；设备被撤销后，即使用户凭证仍有效，也不能通过该设备重新建立隧道。

## 六、设备注册、设备身份与信任状态

### 6.1 设备身份生成

首次启动时客户端生成独立的设备身份密钥对，并为设备创建稳定的本地标识。设备标识不能仅由 MAC 地址、主机名或可变网卡信息生成，因为这些值可能变化、重复或被伪造。

设备身份密钥用于控制面设备证明、请求签名或设备凭证相关操作；WireGuard 私钥用于隧道。两类密钥必须分离，拥有不同的用途、轮换规则和撤销语义。

### 6.2 密钥存储策略

优先使用操作系统提供的安全存储能力：例如 Windows 的受保护凭证/密钥设施、macOS Keychain，以及 Linux 上适用的 Secret Service 或权限受限文件方案。具体实现应以目标平台可用能力为准。

若必须使用本地文件保存私钥，文件应由 Agent 服务账户拥有，权限仅允许该账户读取，目录不可被普通用户写入；写入应采用临时文件、权限设置、原子替换等流程。日志、崩溃报告、诊断包、配置导出和升级日志均不得包含私钥、完整访问令牌或恢复凭证。

操作系统安全存储可降低密钥被普通进程读取的风险，但不能保证在已取得本机管理员权限或系统被完全攻陷时密钥绝对安全。设备合规和信任判断仍应结合服务端策略与可获得的可信证据。

### 6.3 设备注册流程

1. 用户完成身份认证后，客户端生成或加载设备身份公钥。
2. 客户端提交注册请求，包含注册凭证、设备公钥、客户端版本、操作系统类型、设备标识及必要的审计元数据。
3. 控制面校验注册凭证有效期、使用次数、绑定范围、用户注册权限及公钥冲突。
4. 如需要管理员审批，控制面将设备置为待审批状态，客户端显示等待结果，不建立正式网络访问。
5. 审批通过后，控制面绑定用户、设备与企业实例，签发设备凭证或激活设备身份。
6. 客户端保存设备凭证，并使用设备身份向控制面完成后续请求认证。
7. 客户端请求最新设备状态和授权配置；只有在设备状态有效且配置校验通过后，才能进入连接流程。

注册凭证应是限时、限次、可撤销的短期凭证，不能作为长期运行凭证。客户端不得把注册凭证写入诊断日志或在注册完成后继续保留不必要的副本。

### 6.4 设备信任状态处理

客户端必须识别控制面返回的设备状态，例如待审批、可信、受限、已撤销。客户端可以展示状态和执行本地收缩动作，但不能把本地 UI 操作作为设备审批依据。

- **待审批：** 停留在等待状态，不创建正式访问路径。
- **可信：** 可以继续请求当前用户和设备的授权配置。
- **受限：** 只执行控制面明确允许的受限操作；不推断可继续访问原有全部资源。
- **已撤销：** 清理设备凭证的可用状态，断开隧道并移除相关路由/DNS；重新注册须遵循服务端规定。
- **状态未知或无法验证：** 按策略进入受限状态，不把未知状态解释为可信。

### 6.5 设备更换、丢失和密钥轮换

设备更换应创建新的设备身份，不能把旧设备的私钥复制到新设备作为默认迁移方式。设备丢失或密钥泄露时，管理员从控制面撤销设备，网关移除对应 Peer，客户端在收到撤销通知或下次同步时停止访问。

密钥轮换应包含新密钥生成、新公钥登记、控制面确认、配置更新、连接验证和旧密钥撤销。轮换失败时，不应同时永久保留新旧密钥；需根据当前风险和连接状态执行受控回退或进入断开状态。

## 七、控制通道与配置同步

### 7.1 控制通道职责

控制通道承载用户/设备认证后的控制请求、配置拉取、心跳、撤销通知、连接状态上报和诊断事件。普通业务流量不应通过控制 API 转发；业务流量走 WireGuard 数据通道或后续明确设计的应用代理路径。

首期可采用 HTTPS REST API 进行请求响应式交互，并使用长轮询、SSE 或受认证的 gRPC 流承载状态通知。具体机制取决于控制面能力，但客户端必须支持超时、重连、幂等请求、服务端限流和版本兼容。

### 7.2 控制通道安全要求

- 强制验证 TLS 证书链、服务端主机名和有效期。
- 每次请求携带短期用户会话或设备身份凭证，并校验令牌用途、受众和有效期。
- 对高敏感设备操作使用设备密钥签名或等效的设备证明机制。
- 设置连接超时、请求超时、最大响应体大小和合理的重试上限。
- 对重试使用指数退避和随机抖动，避免网络故障时形成请求风暴。
- 仅对明确可重试的错误进行重试；认证失败、签名失败和配置非法不能无限重试。
- 远端响应作为不可信输入处理，必须进行 schema、范围、长度和资源限制校验。

### 7.3 配置内容与完整性

授权配置至少应表达：配置摘要、设备标识、生成时间、有效期或刷新要求、WireGuard 参数、Peer 信息、隧道地址、批准的路由、DNS 配置、必要的本地过滤要求、策略摘要及 schema 兼容信息。

配置不应携带网关或其他设备的私钥。客户端只需要本机 WireGuard 私钥与远端公钥/Endpoint 等连接参数。服务端下发配置应绑定目标设备；在线应用前应确认配置摘要仍等于数据库当前摘要。客户端拒绝设备 ID 不匹配、过期、签名或摘要校验失败，或包含未知高风险字段的配置。`schema_version` 用于结构兼容，不代表业务配置历史版本。

若使用签名配置，签名覆盖规范化后的完整配置内容与关键元数据；客户端应校验签名密钥版本及轮换状态。即使控制通道使用 TLS，配置层签名仍可为缓存配置、离线诊断和跨组件传递提供额外完整性保障，但其实施应与控制面协议统一设计。

### 7.4 配置同步流程

1. Agent 通过控制通道提交设备 ID、最近应用的配置摘要、客户端版本和当前运行状态。
2. 控制面验证用户会话、设备凭证、设备状态及当前策略，计算该设备可获得的授权配置。
3. 控制面返回当前完整配置，并标识目标设备、配置摘要、有效期和完整性信息。
4. 客户端校验响应结构、签名、摘要、设备绑定、地址范围、路由冲突和平台能力。
5. Config Manager 将配置转换为内部期望状态，与当前实际状态进行差异计算。
6. Agent 按安全顺序应用 WireGuard、路由、DNS 和必要的本地保护配置。
7. 完成后读取操作系统实际状态并验证关键项，只有通过验证才将该摘要标记为已应用。
8. 客户端向控制面回报成功、失败阶段、实际应用摘要和标准错误码。
9. 若配置过期、策略撤销或数据库当前摘要变化，客户端按策略收缩旧授权并应用当前配置。

### 7.5 当前配置摘要与兼容性

客户端记录最近获取的期望摘要和本机实际应用摘要。在线应用前应重新确认摘要仍对应数据库当前配置；任务或响应中的旧摘要不能覆盖当前状态。相同摘要重复执行必须幂等。客户端不比较递增业务配置号，也不保存历史配置内容。`schema_version` 和最低 Agent 版本只用于协议/格式兼容。

对于不认识的强制安全字段，客户端应拒绝应用；对于明确标记为可忽略的扩展字段，可按协议兼容规则处理。客户端版本低于配置所需的最低版本时，应提示升级并按服务端策略拒绝建立不兼容连接，而不是忽略安全约束。

### 7.6 离线策略

控制通道短暂中断时，是否保留已建立隧道取决于企业安全策略和授权配置有效期。推荐在首期明确配置有效期和离线宽限规则：

- 允许短暂离线：可在有效期内维持已经授权的连接，但不得扩大访问范围。
- 超过有效期：停止使用过期授权，断开或收缩隧道和路由。
- 已收到撤销信号：立即执行撤销，不受一般离线宽限策略覆盖。
- 从未获取过有效配置：不能因控制面不可达而使用默认路由或宽泛访问范围。

客户端本地缓存只用于恢复已验证配置，不能成为绕过服务端授权的永久授权来源。

## 八、WireGuard 隧道与网络配置管理

### 8.1 隧道管理职责

客户端负责管理本机 WireGuard 隧道的创建、配置、启动、停止、状态查询和异常恢复。它不应把隧道连接成功等同于资源访问成功，也不应根据用户输入任意 Endpoint、AllowedIPs 或网段来扩大访问范围。

WireGuard 负责数据加密和 Peer 级网络通道。用户身份、设备信任、资源级授权和审计仍由 VeloTrust 控制面及网关执行。客户端本地的网络配置是授权的执行结果，而不是授权决策的来源。

### 8.2 WireGuard 配置管理

客户端按授权配置管理以下信息：

- 本机 WireGuard 私钥的安全存储引用。
- 本机隧道地址、接口名称、MTU 和监听/端口相关参数（按平台能力）。
- 网关或对端 Peer 的公钥、Endpoint、AllowedIPs 和必要的保活参数。
- 连接所需的 DNS、路由及平台特定网络参数。
- 最近期望配置摘要、实际应用摘要、最后一次应用结果和错误状态。

WireGuard 私钥应在本机生成和保存，原则上不上传控制面。控制面需要公钥与设备关系来生成 Peer 配置。配置更新时，客户端应使用 WireGuard 管理接口或受控平台 API 完成修改，避免把秘密材料写入命令行参数或普通临时文件。

### 8.3 AllowedIPs 与访问控制

`AllowedIPs` 参与 WireGuard 的路由选择和源地址约束，但不等同于完整业务授权。客户端必须确保 AllowedIPs 来自已校验的授权配置，并与批准路由一致；服务端网关仍需执行 ACL/防火墙规则，阻止超出资源授权范围的流量。

客户端不能仅因为用户配置了某个 CIDR 就向该网段添加路由。需要校验：

1. CIDR 格式正确且地址范围合法。
2. 网段属于控制面批准的资源或网络范围。
3. 与本地直连网段、隧道地址池、其他虚拟接口和已有路由不存在未处理的冲突。
4. 不包含未授权的默认路由 `0.0.0.0/0` 或 `::/0`。
5. 若企业明确配置全隧道模式，应展示该模式并按策略处理 DNS、IPv6、断开恢复和失败时的流量行为。

### 8.4 路由配置与回收

路由模块需要记录每一条由 VeloTrust 创建或修改的路由及其原始状态，避免断开时误删系统或其他 VPN 创建的路由。建议使用可识别的路由标记、独立路由表或平台支持的等效机制。

应用路由前，客户端应先校验完整配置和冲突；应用后读取系统实际路由表确认结果。断开或撤销时，仅清理本客户端拥有的路由，并按保存的变更记录恢复被临时修改的系统参数。若恢复失败，应向用户和控制面报告，并提供只读诊断结果。

### 8.5 DNS 配置

企业 DNS 可用于解析内部域名，但配置方式因操作系统而异。平台适配层应明确支持的能力，例如接口级 DNS、分流 DNS 或按域名规则的 DNS。首期优先采用目标平台稳定、可恢复的方式，不应在未经验证的情况下直接覆盖全系统 DNS。

DNS 应用与回收流程包括：记录原有配置、应用企业 DNS、检查解析行为、断开时恢复原配置、恢复失败时报告。对于全隧道或 DNS 分流，必须考虑 IPv4/IPv6、DNS 泄漏、休眠唤醒和网络切换。不能只恢复 IPv4 DNS 而遗留 IPv6 路径。

### 8.6 连接建立流程

1. 校验用户会话、设备状态和授权配置仍然有效。
2. 确认当前没有处于撤销、隔离或配置失败锁定状态。
3. 检查 WireGuard 组件与系统网络能力。
4. 校验隧道地址、Peer、公钥、Endpoint、AllowedIPs、路由和 DNS 配置。
5. 应用必要的安全保护规则，避免配置切换期间流量意外泄漏。
6. 创建或更新 WireGuard 接口和 Peer。
7. 应用获准路由与 DNS 配置，并核验系统实际状态。
8. 检查控制通道、隧道握手及按策略启用的资源探测。
9. 向 UI 报告真实连接状态，向控制面回报实际应用摘要和连接结果。
10. 任一关键安全步骤失败时，执行回滚或进入受限/断开状态，不得显示为完全连接。

### 8.7 断开流程

1. 接收用户断开、会话撤销、设备撤销、配置过期或安全事件指令。
2. 先停止建立新的受保护访问路径，并根据策略阻断相关流量。
3. 关闭或更新 WireGuard 接口/Peer。
4. 清理由客户端创建的路由、DNS 和其他临时网络配置。
5. 读取实际系统状态，确认隧道关闭和临时配置回收。
6. 清理短期会话凭证或将其标记为不可用；设备长期身份可按策略保留。
7. 上报断开原因、配置摘要、执行结果和失败步骤。

若系统路由回收失败，客户端不得隐瞒错误。应尽力确保失效授权不再通过隧道转发，并提示用户完成必要修复；具体兜底动作按平台能力和企业安全策略实现。

## 九、连接状态机、健康检测与故障恢复

### 9.1 状态模型

客户端应使用明确的状态机，而不是由 UI 多处独立维护布尔值。建议至少区分：

- `Stopped`：Agent 未运行。
- `Unconfigured`：缺少有效企业实例配置。
- `Unauthenticated`：没有有效用户会话。
- `Registering`：设备注册中。
- `PendingApproval`：设备等待审批。
- `SyncingConfig`：获取或校验授权配置。
- `Connecting`：正在应用隧道和网络设置。
- `Connected`：关键配置已应用，隧道达到连接条件。
- `Degraded`：部分健康检查失败，但当前连接仍可能在策略允许范围内运行。
- `Disconnecting`：正在清理隧道和系统网络设置。
- `Revoked`：用户会话、设备或访问授权已撤销。
- `Error`：发生需要人工处理或明确恢复动作的错误。

状态转换应集中在 Agent 的状态协调器中。UI 只订阅并展示状态，不独立判断安全权限。非法状态转换应被拒绝并产生结构化错误事件。

### 9.2 健康检查维度

| 维度 | 检查内容 | 失败示例 |
|---|---|---|
| Agent | 进程、内部组件和本地 IPC | 服务崩溃、IPC 不可达 |
| 用户会话 | 凭证有效性、续期结果、服务端撤销状态 | 会话过期、用户被禁用 |
| 设备身份 | 设备凭证、设备信任状态 | 设备撤销、凭证过期 |
| 控制通道 | DNS、TLS、API 延迟、认证和错误码 | 控制面不可达、证书异常 |
| 配置状态 | 数据库当前摘要与实际应用摘要 | 配置未同步、应用失败 |
| WireGuard | 接口存在、Peer 状态、最近握手时间 | 隧道未建立、握手超时 |
| 网络配置 | 路由、DNS、必要的本地保护规则 | 路由缺失、DNS 未恢复 |
| 资源探测 | 受策略允许的目标健康探测 | 隧道正常但目标服务不可达 |
| 系统资源 | CPU、内存、文件句柄和磁盘空间 | Agent 资源耗尽 |

资源探测应使用明确批准的目标和频率，不能扫描企业网段或把客户端变成未经授权的网络探测工具。

### 9.3 网络变化与自动恢复

客户端应监听操作系统网络变化、休眠/唤醒和默认路由变化事件。在网络变化后，重新评估 Endpoint 可达性、隧道握手、路由冲突和 DNS 状态；必要时重新解析 Endpoint、更新 Peer 或重建隧道。

恢复策略应有最大重试次数、指数退避和随机抖动。认证失败、设备撤销、配置签名失败等安全性错误不能通过无限重试解决。若连接无法恢复，应保留明确错误原因，允许用户触发安全的重试或导出诊断。

### 9.4 控制面离线与访问行为

控制面离线不必然意味着 WireGuard 隧道立即失效，但客户端不能无限期使用陈旧授权。具体行为应由授权配置的有效期、企业离线策略和撤销机制共同决定。

- 在有效期内且未收到撤销通知：可按策略维持已建立的连接，但不得扩大访问范围。
- 配置超过有效期：收缩或断开受保护访问，并提示需要重新验证。
- 收到用户/设备撤销通知：优先执行撤销，不能被一般离线宽限覆盖。
- 无法确认本机当前配置是否合法：不应新建连接；必要时进入安全断开状态。

### 9.5 错误分类与用户提示

内部错误应有稳定错误码，至少区分认证失败、MFA 失败、设备待审批、设备撤销、控制面不可达、TLS 校验失败、配置 schema 不兼容、配置签名/摘要失败、WireGuard 初始化失败、路由冲突、DNS 应用失败、权限不足、资源探测失败和系统配置恢复失败。

UI 显示应提供用户可执行的下一步，例如重新登录、等待管理员审批、检查网络、重试连接或联系管理员；不得显示令牌、内部密钥、完整敏感响应或可导致账户枚举的服务端内部细节。

## 十、访问撤销、紧急断开与安全策略

### 10.1 撤销触发条件

客户端应处理以下撤销或收缩事件：用户退出、用户被禁用、会话到期、会话被管理员强制撤销、设备被撤销或隔离、策略不再允许当前资源、授权配置过期、设备凭证失效、发现关键安全配置被篡改，以及客户端版本被服务端禁止。

### 10.2 撤销事件处理流程

1. 通过控制通道接收撤销通知，或在下次同步时发现状态已失效。
2. 验证事件来源、目标设备/会话和事件版本，拒绝不匹配的撤销消息。
3. 将 Agent 状态切换为撤销或受限，阻止新建连接及扩大授权范围。
4. 按事件范围停止相关 Peer、路由或 DNS 配置；对全设备撤销则断开全部受保护访问。
5. 清理相应的短期会话凭证或设备凭证可用状态。
6. 读取系统实际状态确认执行结果，并将结果上报控制面。
7. 若部分清理失败，记录失败步骤并进入受限状态，避免显示为正常连接。

### 10.3 紧急断开能力

客户端应提供用户可触发的断开操作；如企业安全策略需要，可提供管理员强制断开指令。紧急断开不仅是关闭 UI 状态或停止后台进程，还应实际关闭隧道并清理由客户端管理的路由和 DNS。

若未来支持“断开时阻止所有非企业网络流量”的 Kill Switch，应将其作为单独、显式启用并经过平台专项验证的功能。Kill Switch 涉及系统防火墙、IPv6、DNS、系统更新、局域网访问和故障恢复，不应作为首期默认行为或仅通过简单路由操作实现。

### 10.4 防止配置降级和本地篡改

- 只接受与控制面数据库当前状态一致的配置摘要；不匹配时拒绝应用并重新获取当前配置。
- 对配置的设备绑定、签名、有效期、地址范围和关键字段执行校验。
- 检测本地状态文件损坏或不一致时，重新向控制面获取配置，不把损坏数据视为有效授权。
- 对 Agent 二进制和升级包验证签名；生产环境不允许从任意 URL 下载并直接执行更新。
- 不在日志、崩溃转储和诊断包中输出秘密材料。
- 对本地 IPC 做调用方认证和参数校验，防止普通进程滥用高权限 Agent。

### 10.5 终端合规与风险信号

客户端可以采集必要的客户端版本、操作系统版本、Agent 运行状态和企业批准的合规信号。涉及磁盘加密、EDR、越狱/Root、系统完整性等高级判断时，应明确证据来源、可信度和平台限制。

不能仅依赖客户端自行上报的“合规=true”作为强安全证明。若终端处于高权限攻击者控制下，本地 Agent 和上报信息都可能被篡改。高风险设备应由控制面结合企业 MDM/EDR 或其他可信来源进行判定。

## 十一、密钥、凭证与本地数据安全

### 11.1 材料分类

| 材料 | 用途 | 保存原则 |
|---|---|---|
| 设备身份私钥 | 设备证明、请求签名等 | 优先系统安全存储；不上传控制面 |
| WireGuard 私钥 | 本机隧道加密 | 本机生成与保存；与身份密钥分离 |
| 用户访问令牌 | 短期控制面 API 访问 | 尽量只驻留内存；避免持久化 |
| 刷新令牌/长期会话材料 | 会话续期 | 仅在需要时使用系统安全存储，支持撤销和轮换 |
| 设备凭证 | 证明设备已注册 | 受保护保存，带有效期和撤销语义 |
| 注册凭证 | 首次注册 | 限时限次，注册后清理 |
| 企业 CA/配置签名公钥 | 验证服务端或配置 | 作为受信任公钥管理，支持版本与轮换 |
| 诊断信息 | 排障 | 默认脱敏，不包含密钥和完整令牌 |

### 11.2 密钥轮换流程

1. Agent 根据策略或控制面指令生成新密钥，不覆盖当前有效密钥。
2. 将新公钥和密钥版本提交控制面，证明请求由当前设备身份发起。
3. 控制面完成校验并生成包含新公钥的授权配置。
4. 客户端应用新配置并验证隧道连接。
5. 成功后确认新密钥生效，并清理旧密钥的可用状态。
6. 失败时按策略重试或进入安全断开；不得长期保留无法追踪的双密钥状态。
7. 控制面记录轮换审计，客户端记录执行结果但不记录私钥内容。

### 11.3 本地数据最小化

客户端只保存恢复运行所需的最小数据，例如设备 ID、实例绑定信息、最近配置摘要、必要的非秘密配置和有限的运行状态。用户凭证、私钥和敏感会话数据应使用独立安全存储。

日志应限制保留时长和文件权限，并对用户标识、内部资源名称、IP 地址等信息根据企业隐私要求进行脱敏或分级记录。诊断包默认排除浏览历史、任意应用数据、密码、令牌和私钥；如需要包含内部地址，应提供清晰提示并允许管理员按策略控制。

### 11.4 时间与证书校验

证书有效期、令牌过期和签名时间校验依赖系统时间。客户端发现系统时间明显异常时，应提示用户修正时间，并按安全策略阻止无法正确校验的认证流程。不得为了绕过时钟错误而跳过证书、签名或令牌有效期校验。

## 十二、自动更新、安装包与版本兼容

### 12.1 更新能力

更新模块负责检查新版本、下载或接收安装包、校验签名、执行升级、重启服务并报告结果。首期可先采用管理员分发安装包的方式，待核心连接稳定后再启用自动更新。

### 12.2 更新安全流程

1. 从可信控制面获取版本元数据，包括版本号、平台、架构、最低兼容版本、包摘要和签名信息。
2. 下载或读取更新包，限制大小并校验文件类型。
3. 验证包签名和摘要，校验平台与架构匹配。
4. 记录当前版本和可恢复状态，停止或协调现有网络连接。
5. 安装新版本并启动 Agent，执行自检与协议兼容性检查。
6. 验证核心组件、配置读取和必要健康状态。
7. 成功后确认升级；失败则按平台支持能力恢复旧版本或进入安全断开状态，并上报错误。

### 12.3 版本兼容策略

客户端版本与控制面协议应有明确兼容矩阵。控制面可通过最低客户端版本限制不再安全的旧版本。协议变更应先保证向后兼容，再逐步启用新字段或新能力；涉及安全语义的字段不能静默忽略。

桌面 UI 与 Agent 之间也需要协议版本。升级期间若两者版本不匹配，应提示重启或完成升级，不允许 UI 通过旧 IPC 协议发送未定义的高权限请求。

### 12.4 卸载流程

卸载前应提示当前连接状态，并按企业策略断开隧道、回收由客户端创建的路由/DNS、停止服务、删除程序文件和清理不再需要的凭证。若设备在控制面仍登记，应提示管理员从控制面撤销设备，或在卸载流程中通过有效身份执行注销。

卸载程序不得误删其他 VPN、系统网络或用户自行配置的路由。卸载失败或网络恢复失败时，应提供可审计的错误信息与修复指引。

## 十三、日志、监控、诊断与隐私

### 13.1 本地日志

客户端日志采用结构化格式，至少包含时间、级别、组件、事件类型、错误码、请求关联 ID、配置摘要和处理结果。日志内容应能帮助定位失败发生在哪个阶段，而不是只输出“连接失败”。

建议记录：Agent 启停、用户认证结果类别、设备注册状态变化、配置摘要变化、隧道启动/停止、路由/DNS 应用结果、网络切换、撤销事件、升级结果和关键安全错误。

不得记录：密码、MFA 验证码、完整访问/刷新令牌、私钥、注册凭证、会话恢复秘密以及不必要的业务数据。

### 13.2 诊断包

诊断包应包含客户端版本、操作系统版本、Agent 运行状态、控制通道错误类别、配置摘要、WireGuard 状态摘要、路由/DNS 检查结果和经过脱敏的日志片段。导出前应显示包含的信息类别，并允许企业策略限制导出能力。

诊断包默认不包含完整的企业资源列表、任意进程清单、浏览记录或用户文件。导出文件应设置合理的保留期限和访问权限，避免自动上传到未经批准的外部服务。

### 13.3 运行指标

可采集以下指标并按企业部署策略上报：

- Agent 在线时间、重启次数和内部错误数。
- 登录成功/失败类别及认证耗时（不记录秘密内容）。
- 配置获取耗时、配置应用耗时和失败阶段。
- WireGuard 最近握手时间、连接重建次数及收发流量摘要。
- 路由/DNS 应用失败次数、网络切换次数。
- 客户端版本分布和升级结果。

指标应遵循最小必要原则，不采集与安全访问无关的用户活动。指标上报失败不应导致客户端持续高频重试或影响现有安全状态。

### 13.4 审计边界

客户端记录本地操作和执行结果，控制面负责形成权威审计记录。客户端日志可作为辅助证据，但不能取代服务端对登录、策略决策、设备撤销、配置分发和管理员操作的审计。关键操作应通过关联 ID 将客户端事件与控制面任务关联起来。

## 十四、独立开发、测试与生产加固

本阶段先不依赖管理控制台页面。所有关键能力必须能够通过自动化测试、模拟控制面、命令行和平台集成测试验证。

### 14.1 单元测试

重点覆盖：

- 状态机合法与非法迁移。
- 配置 schema、签名、设备绑定、有效期和版本回退校验。
- 路由 CIDR 解析、冲突检测和默认路由限制。
- 重试策略、退避、超时和取消行为。
- 撤销事件校验与幂等执行。
- 日志脱敏与诊断包排除敏感字段。
- UI/Agent IPC 参数校验与权限错误处理。

### 14.2 集成测试

使用模拟控制面与测试 WireGuard/网络适配器验证：

1. 用户认证成功、MFA 需要/不需要、会话过期和撤销。
2. 设备注册成功、待审批、被拒绝、被撤销和重复注册。
3. 获取有效配置、摘要变化、重复配置、旧配置重放和签名错误。
4. 隧道启动成功、Endpoint 不可达、Peer 公钥错误和握手超时。
5. 路由应用成功、网段冲突、权限不足和回收失败。
6. DNS 配置应用、网络切换、断开恢复和 IPv6 场景。
7. 控制面离线、重连、配置过期和离线宽限结束。
8. 客户端升级成功、包签名错误、升级失败和回退。

### 14.3 平台测试

对每个支持的平台，至少验证安装、卸载、普通用户运行、服务权限、重启恢复、睡眠唤醒、Wi-Fi/有线切换、多个 VPN 共存、IPv4/IPv6、DNS 分流、路由冲突和网络恢复。不同操作系统的测试结果不能互相替代。

### 14.4 安全测试

- TLS 中间人、证书过期、主机名不匹配和私有 CA 更新。
- IPC 未授权调用、参数注入和高权限接口滥用。
- 本地配置篡改、旧配置摘要重放和签名密钥轮换。
- 凭证泄露路径检查：日志、崩溃报告、命令行、临时文件和诊断包。
- 设备撤销后旧凭证重放、旧配置恢复和隧道重连尝试。
- 路由/DNS 泄漏、IPv6 绕行、全隧道切换和断开清理。
- 恶意或超大配置、畸形响应、异常重试与资源耗尽。

### 14.5 验收标准

客户端首期至少满足：

- 能在目标平台完成安装、启动、身份注册、登录和退出。
- 未经审批或被撤销的设备不能建立正式访问路径。
- 用户认证成功不直接等于网络授权成功。
- 只有通过完整性、版本、设备绑定和地址范围校验的配置才能应用。
- WireGuard、路由和 DNS 的实际状态可核验，失败有明确错误码。
- 用户退出、会话撤销、设备撤销和授权过期能够触发相应访问收缩或断开。
- 网络切换、休眠唤醒和控制面短时中断能够按策略恢复。
- 私钥、令牌和注册凭证不会出现在普通日志或诊断包中。
- 所有由客户端创建的临时网络配置均有可验证的清理路径。
- 控制面 API、Agent IPC 与桌面 UI 之间有明确版本和兼容策略。

## 十五、与控制面及管理控制台的最后阶段集成

本章对应客户端实施的最后阶段。客户端核心能力、独立测试、平台网络适配与安全加固完成后，再接入完整控制面流程和管理控制台交互。此前应先确定稳定的协议契约，避免因页面或后端接口变动反复修改客户端核心逻辑。

### 15.1 集成前置契约

在核心开发阶段就应以接口文档或协议定义提前约定以下内容，但不要求立即完成完整集成：

- 企业实例发现/绑定方式与控制面基础地址。
- 用户认证、MFA、会话刷新、注销和撤销协议。
- 设备注册、审批、设备凭证和设备状态模型。
- 授权配置 schema、签名方式、当前配置摘要校验和兼容策略。
- WireGuard Peer、隧道地址、AllowedIPs、路由与 DNS 字段语义。
- 配置应用确认、健康状态、错误码、心跳和审计关联 ID。
- 客户端最低版本、升级元数据、签名和失败恢复规则。

### 15.2 控制面集成顺序

1. **认证集成：** 对接登录、MFA、会话续期和撤销，验证认证状态与客户端状态机一致。
2. **设备集成：** 对接设备注册、审批、凭证签发、设备信任状态与设备撤销。
3. **配置集成：** 对接当前配置获取、签名/摘要校验、配置应用确认和状态对账。
4. **网络集成：** 对接控制面生成的 WireGuard Peer、授权网段、DNS 和必要路由配置。
5. **健康与审计集成：** 上报客户端版本、隧道状态、配置摘要、失败阶段和安全事件。
6. **撤销闭环：** 验证用户停用、会话撤销、设备撤销和策略变更能传导到客户端与网关。
7. **升级集成：** 对接版本元数据、安装包签名、升级状态和最低版本策略。

### 15.3 管理控制台集成

管理控制台主要用于管理员查看设备、批准注册、查看客户端版本和在线状态、触发设备撤销、查看配置应用结果与审计事件。客户端自身的 UI 不应直接嵌入管理控制台的管理权限，也不应向普通终端用户暴露管理员功能。

控制台显示的客户端在线状态应来源于控制面最近一次有效心跳和状态上报，并展示最后更新时间；不能把历史上报的“在线”永久视为当前在线。设备撤销、审批和强制断开操作应由控制面执行并留下审计记录。

### 15.4 端到端验收场景

- 用户完成认证，设备审批通过，客户端获取配置并建立隧道，访问获准资源成功。
- 用户登录成功但设备待审批，客户端不建立正式访问路径。
- 用户具备管理后台权限但没有网络访问授权，客户端不能因此访问企业资源。
- 策略收缩后客户端收到新配置，旧路由/Peer 被回收，未授权资源访问失败。
- 设备被撤销后，客户端断开并清理网络配置，网关同步移除相应 Peer/访问规则。
- 控制面暂时不可达时，客户端遵循配置有效期和离线策略，不扩大访问范围。
- 客户端版本低于最低安全版本时，按策略阻止连接或要求升级。
- 配置签名错误、摘要与当前数据库状态不符或设备 ID 不匹配时，客户端拒绝应用并上报原因。
- 用户退出后，本地会话不可继续使用；重新连接必须完成要求的认证和授权步骤。

## 十六、实施阶段与交付物

客户端按以下顺序实施。前四阶段不依赖管理控制台页面；最后一阶段完成控制面和控制台集成。

| 阶段 | 主要工作 | 交付物 | 完成标准 |
|---|---|---|---|
| 第一阶段：客户端核心框架 | Agent 生命周期、状态机、日志、配置模型、IPC 抽象、平台能力检测 | Windows amd64 CLI、配置规范、核心接口和单元测试 | 可查询 Agent 服务状态、诊断和校验配置；不将服务状态误报为隧道状态；UI 不拥有高权限网络能力 |
| 第二阶段：身份与设备 | 设备密钥生成与存储、实例绑定、认证流程抽象、设备注册状态机 | Identity Manager、Auth 模块、模拟认证服务 | 密钥分离且安全保存；注册与审批状态正确；凭证不落普通日志 |
| 第三阶段：网络数据面 | WireGuard 管理、路由/DNS 适配器、连接/断开、配置应用与恢复 | Tunnel Manager、平台 Network Adapter、端到端测试 | 受控配置可建立连接；断开时可清理本客户端管理的网络状态 |
| 第四阶段：独立测试与加固 | 异常恢复、撤销处理、摘要校验、签名校验、诊断包、平台测试和安全测试 | 测试报告、威胁检查清单、生产配置模板 | 关键安全场景通过测试；配置错误不会默认放行；失败可定位 |
| 第五阶段：控制面与管理控制台集成 | 对接认证、设备注册、配置分发、状态上报、审计、撤销和升级；完善 UI | 集成客户端、协议兼容文档、端到端验收报告 | 用户、设备、策略、隧道、网关和审计形成闭环 |

### 16.1 首期建议范围

首期重点完成桌面终端的可信注册、用户认证、WireGuard 受控连接、授权路由/DNS、配置同步、撤销、健康检查和日志诊断。应用级代理、复杂 Kill Switch、移动端、跨平台高级合规检测等扩展能力应在首期闭环稳定后再决定。

### 16.2 关键交付物清单

- 客户端功能需求与状态机说明。
- Agent 模块设计与接口定义。
- 控制面 API 契约与配置 schema。
- UI/Agent IPC 协议。
- 设备身份与密钥生命周期说明。
- WireGuard 与路由/DNS 平台适配实现。
- 安装包、服务配置和升级/卸载方案。
- 自动化测试、平台测试与安全测试报告。
- 日志字段、错误码和诊断包脱敏规则。
- 控制面与管理控制台集成验收报告。

### 16.3 Windows 客户端 CLI 首个增量

首个可运行版本以 Windows amd64 CLI 为入口，先完成只读的本机状态和配置诊断：

| 命令 | 行为 |
|---|---|
| `client-cli version` | 输出版本、操作系统和架构；支持 JSON 输出 |
| `client-cli status` | 只查询 `VeloTrustClientAgent` Windows 服务状态、进程是否提升；明确报告隧道状态尚不可用 |
| `client-cli config validate` | 校验本地配置 schema_version、实例标识、HTTPS 控制面地址和日志级别；拒绝未知字段及超大/非普通文件 |
| `client-cli diagnose` | 汇总平台、提权状态、Agent 服务状态和配置校验结果；支持 JSON 输出 |

首版配置只保存非秘密运行参数，至少包含 `schema_version`、`instance_id`、`control_plane_url` 和可选的 `log_level`。默认路径为 `%ProgramData%\VeloTrust\Client\client.json`，也可通过 CLI 指定配置路径。身份密钥、WireGuard 私钥、令牌和密码不属于该文件。

构建目标固定为 `windows/amd64`，使用 `make build-client-cli-windows` 生成 `bin/client-cli-windows-amd64.exe`。首版 CLI 不提供登录、连接、断开或任意网络修改命令；待后台 Agent、可信授权配置和 Windows 隧道/路由适配完成后，再通过受限 IPC 加入这些操作。CLI 单独成功运行或 Agent 服务处于运行状态都不能作为隧道已连通、资源可达的证明。

## 十七、关键技术边界与最终设计结论

### 17.1 客户端必须做好的事情

1. 可信地识别当前企业实例、用户会话和设备身份。
2. 安全保存设备身份密钥、WireGuard 私钥和必要凭证。
3. 只接受通过认证、设备绑定、完整性和当前摘要校验的授权配置。
4. 将批准的配置转化为可核验的隧道、路由和 DNS 状态。
5. 对网络切换、休眠唤醒、配置失败和控制面中断进行可预测的恢复处理。
6. 在会话、设备或策略撤销时，及时停止或收缩访问并报告实际执行结果。
7. 为用户和管理员提供真实、分层、可诊断的连接状态。
8. 保护本地凭证和隐私，避免在日志、IPC、临时文件和更新流程中产生新的攻击面。

### 17.2 客户端不应承担的职责

- 不自行决定用户最终可以访问哪些资源。
- 不因为用户登录成功就默认允许全部企业网段。
- 不以本地配置文件替代控制面授权和设备状态。
- 不将 WireGuard 隧道握手视为资源可达或授权有效的充分条件。
- 不执行远端传入的任意 Shell 命令或未经校验的网络操作。
- 不将私钥上传控制面，也不把设备身份密钥与 WireGuard 私钥混用。
- 不默认跳过 TLS、配置签名、证书有效期或摘要校验。
- 不在首期无验证地承诺所有桌面、移动和服务器操作系统均可用。

### 17.3 最终结论

VeloTrust 客户端应以 Go 实现可测试的后台 Agent，并将用户交互、设备身份、控制通道、配置管理、WireGuard 和操作系统网络适配解耦。控制面负责身份与授权决策，客户端负责安全地执行本机配置，网关负责执行企业网络边界的访问控制，三者共同形成零信任访问闭环。

推荐实施顺序为：**客户端核心框架 → 身份与设备注册 → WireGuard 与网络配置 → 独立测试和生产加固 → 最后集成控制面与管理控制台**。即使控制台集成安排在最后，认证协议、设备身份、配置 schema、状态上报、撤销和版本兼容契约也必须提前确定。通过这一顺序，可以先验证客户端最关键的安全与网络能力，再完成端到端产品集成，降低 UI 和接口变更对核心实现的返工影响。
