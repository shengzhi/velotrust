# VeloTrust 企业级零信任安全访问平台（ZTNA）技术实现方案

本方案按照业务模块、核心功能、关键技术、业务处理流程、异常处理与安全控制的结构展开，重点说明各模块如何协同实现业务目标，而不是简单罗列代码或技术组件。

整体设计遵循以下原则：

- 控制面与数据面分离：控制面负责身份认证、访问授权、策略管理、节点管理和配置下发；数据面负责隧道建立、数据转发及网络访问。
- 身份可信、设备可信、访问可信：每次访问都依据当前身份、设备状态、访问目标和安全策略进行判断，不以网络位置作为唯一信任依据。
- 基于 WireGuard 构建安全数据通道：利用 WireGuard 实现高性能加密隧道，通过独立控制面管理节点身份、隧道配置、密钥生命周期和访问规则。
- 以 Go 语言实现核心服务：控制面采用模块化服务设计，根据业务边界划分服务与接口；需要跨服务通信时，采用 gRPC 等方式进行调用。
- 以策略驱动访问控制：将用户、设备、网络节点、目标资源和访问规则统一纳入策略管理，支持动态授权、权限回收、配置更新和审计追踪。

需要特别明确：WireGuard 负责加密隧道和数据面的网络转发能力，它本身并不提供完整的企业身份认证、动态授权、设备合规检查或业务审计体系。这些能力需要由 VeloTrust 控制面及其与数据面的协作实现。

## 一、总体技术架构

VeloTrust 采用分层、模块化架构，核心分为管理控制层、业务服务层、网络控制层、数据转发层和基础设施层。各层通过明确的接口协作，避免将身份认证、策略判断、隧道管理和数据转发耦合在同一个服务中。

### 1.1 架构分层与职责

| 架构层    | 核心模块                     | 主要职责                             |
| ------ | ------------------------ | -------------------------------- |
| 管理控制层  | 管理控制台、组织管理、用户管理、资源管理     | 提供企业管理入口，维护组织、身份、网络和资源信息         |
| 身份与授权层 | 身份认证、设备身份、策略引擎、访问授权      | 验证身份与设备，判断访问请求是否满足授权条件           |
| 网络控制层  | 节点管理、隧道编排、配置分发、密钥管理      | 管理 WireGuard 节点、隧道关系、网络地址及配置生命周期 |
| 数据转发层  | WireGuard、访问网关、路由控制、转发节点 | 承载加密流量，实现终端到企业资源的安全访问            |
| 基础设施层  | 数据库、缓存、消息队列、监控、日志、密钥设施   | 提供持久化、状态同步、可观测性和密钥保护能力           |

### 1.2 控制面与数据面的交互机制

控制面不直接承载普通业务流量，而是负责生成并维护数据面运行所需的可信配置。数据面按照已下发的配置建立加密隧道、执行网络路由及转发。

二者的协作过程如下：

1. 管理员创建用户、设备、网络和受保护资源，并维护企业内部组织关系。
2. 用户或设备完成身份认证，控制面建立对应的身份与设备状态。
3. 策略引擎根据身份、设备、目标资源和环境条件计算访问权限。
4. 网络控制模块将授权结果转换为节点、路由、AllowedIPs、访问规则等运行配置。
5. 控制面将配置安全地下发到相关节点，节点验证配置后执行更新。
6. 终端通过 WireGuard 建立加密连接，按照生效的路由和访问规则访问目标资源。
7. 节点持续上报连接状态、配置版本、流量指标和安全事件，控制面据此更新状态或撤销权限。

这里需要区分两个概念：隧道已建立不代表业务访问已获授权，配置已下发也不代表目标业务一定可达。 系统应分别判断身份认证、策略授权、隧道状态、路由可达性和目标服务健康状态。

## 二、组织与用户管理模块

### 2.1 模块目标

本模块负责维护当前 VeloTrust 部署所服务企业的基本信息，以及企业内部的用户、团队、管理员和资源归属关系。每个部署实例仅服务一个企业；不同企业通过独立实例及其基础设施边界隔离。

### 2.2 关键功能

- 当前企业的基本信息维护。
- 组织部门、团队和用户归属关系维护。
- 企业管理员、网络管理员、安全管理员等管理职责划分。
- 用户、设备、网络、资源及策略的组织归属关系维护。
- 管理操作审计及组织成员状态变更通知。

### 2.3 关键技术

身份与组织范围传递。 每次管理请求均应从已验证的会话中取得操作者身份和角色，服务端不能直接信任客户端传入的用户或组织标识。经验证的身份和组织授权范围应贯穿 API、gRPC、数据库查询和异步任务。

数据归属与访问控制。 当前部署实例中的业务数据统一归属于该实例所服务的企业。业务表按实际关系维护用户、组织、设备、网络、资源和策略的关联，并通过服务端 RBAC 和资源范围校验限制操作；企业之间通过独立部署隔离。

组织与权限解耦。 组织关系用于表达用户归属和管理范围，RBAC 用于表达用户可执行的管理操作，网络访问策略则用于控制用户能够访问哪些业务资源。这三者不应混为一体。

### 2.4 业务流程

1. 平台管理员初始化当前部署的企业基本信息、首个管理员、默认管理角色和基础安全配置。
2. 企业管理员通过邀请或配置的身份源同步方式加入成员，并将成员分配到组织部门。
3. 管理员为成员授予管理角色，但不会因此自动获得对全部企业网络资源的访问权限。
4. 用户申请访问资源时，系统校验其账户状态、组织状态、设备状态和网络访问策略。
5. 用户、组织或身份源被停用时，系统阻止新的认证及授权，并按撤销策略清理相关会话、设备授权和隧道配置。

停用用户或组织成员关系不能只修改数据库中的状态字段，还必须触发后续的授权撤销和数据面配置收敛流程。

## 三、身份认证与会话管理模块

### 3.1 模块目标

身份认证模块用于确认访问主体的真实身份，并为后续设备绑定、策略计算和网络访问提供可信的身份上下文。

该模块需要覆盖用户登录、二次认证、设备注册、会话管理、身份失效和凭证撤销等完整生命周期。

### 3.2 关键功能

- 用户名密码认证及密码安全管理。
- 多因素认证，包括 TOTP、一次性验证码等适用方式。
- 企业身份源集成，例如 OIDC、SAML 或企业目录服务。
- 登录风险判断、异常登录限制及认证失败保护。
- 会话创建、续期、过期、注销和强制失效。
- 用户禁用、凭证撤销及认证状态变更通知。
- 设备注册和设备身份凭证签发的前置认证。

### 3.3 关键技术

认证与授权分离。 身份认证模块只回答“当前主体是谁、凭证是否有效”；是否允许访问某个网络或业务资源，应交由策略引擎判断。

短期访问凭证与长期身份凭证分离。 用户登录凭证用于证明用户身份；设备凭证用于证明设备身份；用于管理 API 的访问令牌则应设置有效期、受众和权限范围。不能将长期设备私钥直接作为用户登录凭证使用。

会话状态管理。 可使用短期令牌结合服务端会话状态的方式，兼顾请求验证效率与主动撤销能力。对于高风险操作，应重新验证身份或要求二次认证。

凭证保护。 密码采用适当的专用密码哈希算法保存；TOTP 密钥、恢复凭证及其他高敏感认证材料需要加密保护，并限制可访问它们的服务和管理员。

### 3.4 业务流程：用户登录到建立可信身份

① 用户发起登录

提交登录凭证、设备标识及必要的环境信息

② 认证服务验证身份

检查账户状态、密码或外部身份源返回结果、认证失败次数

③ 风险与二次认证判断

根据安全策略决定是否需要 TOTP 或其他二次验证

④ 建立用户会话

生成短期访问凭证，记录登录事件和会话状态

⑤ 进入资源访问授权流程

后续仍需完成设备验证、策略评估和网络配置

具体处理过程如下：

1. 用户通过管理门户或客户端提交登录请求，认证服务根据当前部署配置的身份源及用户标识定位账户。
2. 服务端检查账户是否启用、是否锁定，以及密码、外部身份断言等认证材料是否有效。
3. 若策略要求多因素认证，则创建有时效限制的待验证状态；二次认证通过后才能完成登录。
4. 登录成功后，系统创建会话并记录登录时间、认证方式、设备信息及风险结果。
5. 客户端使用访问凭证调用受保护的 API；服务端验证凭证后，还要校验其有效状态和权限范围。
6. 用户退出、账户被禁用、会话到期或安全管理员执行强制注销时，系统使相关会话失效，并通知后续授权与网络控制模块。

需要注意，JWT 令牌一旦签发，单纯修改数据库状态不会自动使所有独立验证方立即拒绝该令牌。若要求即时撤销，需要采用短期令牌、会话状态校验、撤销列表或等效机制。

## 四、设备身份与设备信任模块

### 4.1 模块目标

设备管理模块解决“哪台设备正在请求访问”的问题。它与用户身份相互独立：同一个用户可以拥有多台设备，而同一台设备的状态也可能随时间变化。

设备身份模块需要建立设备唯一身份、设备凭证、注册关系和信任状态，并为访问策略提供可验证的设备上下文。

### 4.2 关键功能

- 设备注册、审批、绑定、解绑和注销。
- 设备唯一标识及设备公私钥管理。
- 设备凭证签发、续期、撤销和轮换。
- 设备信任状态管理，如可信、待审批、受限、已撤销。
- 设备心跳、最近在线时间和客户端版本采集。
- 可选的操作系统版本、终端安全状态及合规检查集成。
- 设备丢失、密钥泄露或异常行为时的快速隔离。

### 4.3 关键技术

设备密钥与用户密码分离。 推荐由客户端生成设备密钥对，私钥尽量保留在终端的安全存储中，控制面只保存公钥及设备元数据。若使用 WireGuard，每个设备或网络节点的 WireGuard 公钥都应有明确的所有者、用途和生命周期。

设备信任状态机。 设备状态应通过明确的状态迁移控制，例如“待注册 → 待审批 → 已可信 → 受限/已撤销”。每次状态迁移均需校验操作者权限、前置状态和业务条件。

设备合规检查。 如果需要判断磁盘加密、终端防护或操作系统安全状态，应通过受信任的客户端、管理代理或企业终端管理系统获取证据。仅依赖客户端自行上报的字符串不能证明设备真实合规。

### 4.4 业务流程：设备注册与可信化

1. 用户完成身份认证后，客户端生成设备密钥对，并提交设备注册请求。
2. 控制面验证用户是否有权注册设备，以及当前实例的设备注册规则、审批要求和安全策略是否允许注册。
3. 系统创建设备记录，将设备公钥、所属用户、所属组织、客户端版本及注册来源关联起来。
4. 对需要审批的设备，进入待审批状态；审批通过后签发设备凭证或激活设备身份。
5. 设备首次连接时，控制面验证设备凭证，并确认设备未被撤销、未超过允许期限。
6. 策略引擎结合设备信任状态计算该设备可访问的网络及资源范围。
7. 设备丢失、异常或被管理员撤销时，控制面将设备标记为不可用，撤销相关授权，并通过配置分发机制移除对应的网络访问能力。

设备在线状态不能直接等同于设备可信状态。心跳正常只能说明设备近期可达；是否允许访问仍需依据身份、设备状态和当前策略综合判断。

## 五、资源目录与网络拓扑管理模块

### 5.1 模块目标

资源目录用于描述企业希望通过 VeloTrust 访问的对象；网络拓扑用于描述这些资源位于何处，以及终端应通过哪些节点和路由到达目标。

两者应分开建模。业务资源是授权对象，网络拓扑是实现访问的技术路径。一个业务资源可以对应多个 IP、域名或端口，也可能因为高可用部署而对应多个网关。

### 5.2 关键功能

- 创建和维护企业网络、子网、网段及网络区域。
- 登记受保护资源，包括服务器、数据库、应用系统、域名和指定端口。
- 关联云环境、VPC、数据中心及本地网络。
- 配置资源标签、所属部门、业务重要级别和安全分类。
- 管理资源与访问网关、出口节点之间的关联关系。
- 检查网段冲突、路由重叠和资源地址变更。
- 维护资源发现结果与人工登记结果之间的对应关系。

### 5.3 关键技术

资源抽象模型。 建议将业务资源抽象为独立实体，并将 IP、端口、协议、域名和路由信息作为资源的访问端点或网络映射。不要把单个 IP 地址直接当作完整的业务资源，否则难以表达同一应用的多实例、高可用及动态地址变化。

网络地址规划。 WireGuard 节点使用的隧道地址、企业内部业务网段以及客户端本地网段需要统一规划。创建网络时就应检查 CIDR 重叠，并制定冲突处理和路由优先级规则。

资源发现与人工确认。 可通过云平台 API、CMDB 或网络扫描获取资源信息，但发现到的资产不应自动成为所有用户可访问的资源。资源纳管和访问授权应是两个独立流程。

### 5.4 业务流程：资源纳管

1. 管理员创建企业网络，定义网络名称、CIDR、所属云环境和网络区域。
2. 系统校验网段是否合法，并检查与当前实例已登记的企业网络、隧道地址池和路由范围是否冲突。
3. 管理员新增受保护资源，指定其域名或 IP、端口、协议及所属网络。
4. 系统根据资源所在网络，确定可用的访问网关或连接节点。
5. 管理员为资源添加业务分类和安全标签，供策略引擎进行条件匹配。
6. 系统执行连通性检查，确认资源映射、网关路径和路由信息是否完整。
7. 资源进入可供授权策略引用的状态；后续资源地址变化时，系统重新评估相关路由和授权配置。

资源纳管成功只代表资源目录中已存在该对象，并不意味着访问网关已具备可达性，也不意味着任何用户已经获得访问权限。

## 六、访问策略引擎与授权管理模块

### 6.1 模块目标

策略引擎是 VeloTrust 实现零信任访问控制的核心。它负责综合评估用户身份、设备状态、访问资源和环境条件，生成明确的授权决策，并将决策转化为数据面可以执行的配置。

该模块需要把“谁可以访问什么、在什么条件下访问、通过什么路径访问”从静态网络配置中独立出来。

### 6.2 关键功能

- 创建、修改、启用、停用和删除访问策略。
- 基于用户、用户组、组织、设备、设备状态和资源标签进行匹配。
- 配置访问目标、协议、端口、访问时间段及可选的风险条件。
- 支持允许、拒绝、附加认证、限制访问等策略效果。
- 管理策略优先级、冲突处理和默认拒绝规则。
- 对策略进行预检查、模拟评估、版本管理和变更审计。
- 支持授权有效期、定期复核和临时访问到期回收。

### 6.3 关键技术

策略决策与策略执行分离。 控制面负责计算授权结果，数据面负责落实网络层的执行规则。策略引擎不应直接在每个数据包上调用数据库查询，而应将计算结果编译为数据面能够高效执行的配置。

默认拒绝。 当请求缺少必要的身份、设备或资源信息时，应默认拒绝访问，而不是自动放行。策略服务不可用时的行为也必须明确，尤其是新授权请求与已有连接应分别定义处理规则。

策略版本化。 每次修改都生成新的策略版本，并记录变更人、变更时间、变更内容和影响范围。下发前可比较新旧版本的有效授权集合，识别可能导致权限扩大或网络中断的变化。

授权粒度分层。 至少应区分管理 API 权限、网络连接权限和业务资源权限。管理控制台的管理员权限不能直接等价为任意网络访问权限。

### 6.4 业务流程：策略创建与访问授权

① 创建访问策略

选择主体、设备条件、资源、协议、端口及有效期

② 策略校验与冲突分析

检查资源引用、规则优先级、冲突和权限范围

③ 发布策略版本

保存审计记录，计算受影响的用户、设备和网络节点

④ 生成授权决策与执行配置

确定允许的资源范围，编译路由及数据面访问规则

⑤ 配置生效与状态确认

节点应用配置并回报版本，系统跟踪未生效节点

详细业务处理过程：

1. 管理员创建策略，指定用户或用户组、允许访问的资源以及适用的设备和环境条件。
2. 服务端校验策略引用的主体、设备组、资源和网络是否存在且有效，并检查规则冲突。
3. 策略发布服务生成不可混淆的策略版本，保存变更记录，并计算新版本影响的授权关系。
4. 策略引擎将策略转换为具体的授权结果，例如允许某用户的某设备通过指定网关访问某资源的 TCP 443 端口。
5. 网络控制模块据此生成隧道、路由和访问控制配置，推送至相关节点。
6. 节点应用配置后报告实际生效的版本和执行结果。控制面只有收到足够的确认信息，才能将对应节点标记为已同步。
7. 用户发起访问时，控制面或客户端获取有效的授权配置；数据面按照已生效的规则执行访问限制。
8. 策略变更或撤销时，系统重新计算受影响的授权集合，删除不再允许的路由或访问规则，并按要求处理已有连接。

必须注意：WireGuard 的 `AllowedIPs` 同时涉及对端流量的路由选择和源地址约束，但它不是完整的应用层授权引擎。 如果需要限制同一隧道内只能访问指定 TCP/UDP 端口，应结合主机防火墙、网关 ACL、网络过滤机制或相应的代理策略执行，不能仅依赖 WireGuard 对端配置。

## 七、WireGuard 隧道与网络节点管理模块

### 7.1 模块目标

隧道管理模块负责将逻辑访问授权转化为实际可用的加密网络连接。它需要维护终端、边缘节点、网关及中继节点之间的连接关系，并管理隧道地址、密钥、公钥、Endpoint 和 AllowedIPs 等配置。

### 7.2 关键功能

- WireGuard 节点注册、身份认证和生命周期管理。
- 隧道地址池分配及地址冲突检测。
- 节点公钥登记、密钥轮换和密钥撤销。
- Peer 配置生成、更新和删除。
- 节点间连接关系与网络拓扑管理。
- Endpoint 发现、NAT 环境适配和持久连接配置。
- 节点健康检测、连接状态采集和故障切换。
- 隧道配置版本管理及配置应用确认。

### 7.3 关键技术

WireGuard 配置管理。 控制面保存逻辑配置与期望状态，通过受控代理或本地节点服务将配置应用到 WireGuard。应优先使用结构化配置接口，避免通过拼接 Shell 命令直接操作隧道配置。

密钥生命周期管理。 WireGuard 私钥原则上应在使用它的节点本地生成并保存，控制面主要维护公钥和关联元数据。需要集中托管密钥时，应采用专门的密钥保护措施，并严格限制密钥导出、访问和轮换权限。

期望状态与实际状态对账。 控制面维护期望配置，节点报告实际配置版本和运行状态。后台对账任务发现偏差后，可重试下发、触发修复或告警，避免将“已发送配置”误判为“配置已生效”。

配置变更原子性。 涉及 Peer、路由和防火墙的变更应设计一致的应用顺序，尽量避免新旧规则切换时出现意外放通或断网。对重要网络变更，应支持预检查及必要的回滚机制。

### 7.4 业务流程：终端隧道建立

1. 客户端完成用户认证和设备身份验证，申请建立目标网络连接。
2. 控制面检查用户会话、设备状态和访问策略，确认目标资源及其所在网络。
3. 网络控制模块选择满足网络可达性和安全要求的节点，并分配或确认隧道地址。
4. 客户端生成或读取本地 WireGuard 密钥，向控制面提交公钥和必要的连接信息。
5. 控制面为相关 Peer 生成配置，包含对端公钥、允许的地址范围、Endpoint 以及必要的保活参数。
6. 节点通过受认证的控制通道获取配置，验证配置版本及完整性后应用到 WireGuard。
7. 客户端启动隧道并通过握手、路由检查和目标连通性测试验证连接。
8. 控制面分别记录配置同步状态、隧道握手状态和目标业务可达状态。
9. 若握手失败，则检查密钥、公网 Endpoint、防火墙、NAT 和网络连通性；若握手成功但业务不通，则继续检查路由、ACL 和目标服务。

这里需要强调，WireGuard 的握手信息并不能完全替代业务可达性检测。系统应分别监控“节点可达”“隧道握手成功”和“业务访问成功”三个层次。

## 八、配置分发与节点状态同步模块

### 8.1 模块目标

配置分发模块负责把控制面的策略、隧道、路由和节点管理结果可靠地同步到分布式数据面。该模块直接影响策略是否真正生效，因此不能只实现一个简单的配置下载接口。

### 8.2 关键功能

- 配置版本生成、存储和差异计算。
- 节点配置订阅、拉取、推送及变更通知。
- 配置完整性校验和节点身份校验。
- 配置应用状态上报、超时重试和失败告警。
- 节点离线期间的配置积压与恢复同步。
- 策略撤销和设备撤销的高优先级传播。
- 节点实际状态与控制面期望状态的持续对账。

### 8.3 关键技术

控制通道与数据通道分离。 配置下发使用独立的认证通信通道，不依赖待建立的业务隧道，否则可能出现隧道尚未建立就无法取得隧道配置的循环依赖。

版本号与幂等操作。 每次配置发布均带有版本号或唯一变更标识。节点重复收到同一版本时，应能安全地重复处理；收到过期版本时，应拒绝覆盖较新的有效配置。

可靠投递。 可通过消息队列、持久化任务表或可靠事件机制记录待分发任务。推送消息用于通知节点有新配置，节点确认、配置版本查询和后台重试机制负责保证最终收敛。

撤销优先级。 普通配置优化与安全撤销不能使用完全相同的调度优先级。对于账户禁用、设备失陷和高风险策略撤销等事件，应尽快传播，并记录传播延迟和未确认节点。

### 8.4 业务流程：策略更新后的配置同步

1. 策略发布服务提交新的策略版本。
2. 配置编排服务计算新版本与旧版本之间的差异，识别需要增加、修改或删除的 Peer、路由和 ACL。
3. 系统将变更拆分为可执行的节点任务，写入持久化任务记录。
4. 通过 gRPC 流式通信或消息通知提示节点获取新版本。
5. 节点验证身份、配置版本和完整性，检查配置的基本合法性。
6. 节点应用配置并进行必要的运行状态检查，随后返回成功或失败结果。
7. 控制面更新各节点的实际生效版本；失败任务根据错误类型执行重试或告警。
8. 对未确认节点持续执行对账；对于涉及撤权的任务，根据安全要求采取隔离节点、阻断访问或限制旧配置继续使用的措施。

不能把“配置下发成功”直接等同于“访问权限已撤销”。应以节点实际执行状态、连接处理策略和可验证的撤销结果作为判断依据。

## 九、网络接入网关与数据转发模块

### 9.1 模块目标

数据转发模块负责把终端产生的加密流量安全地送达企业内部服务，并确保实际转发路径与控制面的授权结果一致。

对于不同的网络环境，可部署客户端直连型网关、站点接入网关和中继节点。具体部署方式取决于目标资源所在网络、网络地址冲突情况、NAT 环境和可用性要求。

### 9.2 关键功能

- 终端到企业网络的加密流量转发。
- 企业内网网段和指定业务资源的访问。
- 网络路由、源地址处理及必要的 NAT。
- 基于目标地址、协议和端口的访问控制。
- 跨网段访问与站点间互联。
- 网络连接跟踪、流量统计及异常流量检测。
- 访问网关健康检查及故障切换。
- 防止未经授权的横向移动和跨网络访问。

### 9.3 关键技术

三层隧道与应用代理的边界。 WireGuard 主要提供三层 IP 隧道。对于 SSH、RDP、数据库连接等基于 TCP/UDP 的网络访问，可以通过路由和网关过滤实现访问控制；对于 HTTP 应用级身份校验、URL 级授权或精细化内容控制，则需要额外部署七层代理或应用侧控制。

路由与授权联动。 仅下发路由不代表访问安全，必须同步部署与授权结果一致的访问过滤规则。对已撤销的资源授权，应删除相应路由或过滤规则，并根据要求处理已建立的连接跟踪状态。

网络隔离。 不同安全域和不同业务网络应具有明确的隔离边界。共享网关需要依据已验证的身份和访问策略执行授权，并在操作系统网络命名空间、路由表或防火墙规则层面落实必要的网络隔离措施。

高可用。 网关应具备健康检测和故障恢复机制。对于多网关环境，应明确路由切换、连接重建和会话中断的行为，避免把网关切换误认为现有 TCP 连接必然无损迁移。

### 9.4 业务流程：访问企业内部资源

1. 用户在客户端选择目标业务资源，客户端根据已生效的配置确定访问路径。
2. 客户端将业务流量发送至对应的 WireGuard 隧道。
3. 访问网关解密收到的隧道流量，并根据目标地址、协议、端口和当前生效的 ACL 检查是否允许转发。
4. 如果目标位于本地直连网段，网关将流量路由到目标服务器；如果目标位于其他站点或云网络，则按照预先配置的路由转发。
5. 目标服务处理请求，并按照正常网络路径返回响应。
6. 返回流量经过相应的路由及隧道返回客户端。
7. 网关记录必要的连接元数据、流量统计和安全事件，但不默认记录业务载荷。
8. 如果访问被拒绝、目标不可达或网关故障，系统记录对应原因，供客户端和管理平台排查。

业务访问异常需要区分以下情况：

- 隧道无法建立：检查节点身份、密钥、Endpoint 和网络可达性。
- 隧道正常但无法访问：检查路由、ACL、NAT 和目标服务。
- 访问被策略拒绝：检查授权结果及配置版本。
- 访问中途断开：检查连接状态、策略撤销、网关切换及目标服务异常。

通过分层定位，可以避免将所有连接失败都归因于 WireGuard 隧道本身。

## 十、NAT 穿透与中继节点模块

### 10.1 模块目标

在企业多云及跨地域组网环境中，终端或网关可能位于 NAT、动态公网地址、受限防火墙或运营商网络之后。该模块负责提高节点之间建立安全通道的成功率，并在无法直接通信时提供可控的中继路径。

### 10.2 关键功能

- 节点 Endpoint 发现及变化检测。
- NAT 环境下的连接保持和重连。
- 直连链路可用性检测。
- 中继节点注册、健康检查和负载管理。
- 直连优先、中继兜底的连接策略。
- 中继流量统计、容量控制和故障切换。

### 10.3 关键技术

WireGuard 并不自带完整的 NAT 穿透协调服务或中继网络。VeloTrust 需要实现相应的控制逻辑，并在必要时提供 UDP 中继或其他受控转发能力。

直连优先。 控制面收集节点的连接信息，协调节点尝试建立直接 UDP 通信。在 NAT 环境下，可根据网络情况配置适当的持久保活参数，以减少 NAT 映射过期导致的连接中断。

中继兜底。 当直接连接不可用时，节点通过已认证的中继通道传输 WireGuard 加密数据报。中继只负责转发，不应因此获得解密业务流量的能力。

连接质量评估。 综合 RTT、丢包率、可达性、节点负载和出口带宽，选择满足业务要求的路径。路径探测应设置超时和频率限制，避免增加不必要的控制流量。

### 10.4 业务流程：直连失败后的中继切换

1. 两个节点向控制面登记身份、公钥和可用的网络端点。
2. 控制面协调双方尝试建立直接 UDP 通信。
3. 节点通过 WireGuard 握手结果、网络探测及必要的连通性检查判断直连是否成功。
4. 在限定时间内未能建立连接时，控制面根据策略分配可用中继节点。
5. 双方切换到中继路径，通过中继转发加密数据报。
6. 系统持续监控中继负载和链路质量，并在条件满足时尝试恢复直连。
7. 中继故障时，系统重新选择中继或通知节点重新连接，并记录切换事件。

中继切换的实现方式需要结合客户端能力和部署环境设计。不能假设只要修改 WireGuard 的 Endpoint，就能自动完成所有类型的 NAT 穿透。

## 十一、密钥与安全凭证管理模块

### 11.1 模块目标

该模块负责管理设备身份凭证、节点公钥、WireGuard 私钥保护、服务间认证凭证以及其他敏感密钥的生命周期，防止密钥泄露、越权使用或长期不轮换造成的安全风险。

### 11.2 关键功能

- 节点密钥注册与公钥关联。
- 私钥生成、存储、使用及轮换。
- 设备凭证和服务间凭证签发与撤销。
- 高敏感凭证的加密保存及访问控制。
- 密钥到期提醒、轮换任务和异常访问告警。
- 密钥泄露后的快速隔离与配置更新。
- 密钥操作审计和职责分离。

### 11.3 关键技术

密钥分级管理。 区分用户认证凭证、设备注册/会话凭证、节点 WireGuard 密钥、服务间认证凭证和数据库加密密钥。Gateway/Client 节点只生成一对长期 WireGuard 密钥；其公钥作为节点网络身份标识，不再额外生成 Ed25519 节点身份密钥。注册凭证和短期会话凭证用于控制面认证，不能与 WireGuard 私钥混为一谈。

最小化密钥暴露。 设备私钥尽量在本地生成并保留；控制面通过公钥识别节点。对于必须集中管理的密钥，可采用 KMS 或 HSM 等设施，并限制密钥导出和使用权限。

轮换与配置协调。 密钥轮换应具备新旧凭证过渡、节点配置同步和失败回滚或重新注册机制。轮换成功的判定必须包括节点实际应用新公钥，而不只是数据库中的公钥字段已被更新。

### 11.4 业务流程：节点密钥轮换

1. 节点或控制面根据轮换计划创建密钥轮换任务。
2. 节点生成新密钥对，并通过已认证的控制通道提交新公钥。
3. 控制面校验节点身份和轮换任务，将新公钥纳入待发布配置。
4. 控制面向相关 Peer 下发新公钥配置，等待节点确认。
5. 根据部署方式执行新旧密钥过渡，验证新密钥对应的 WireGuard 握手和连接状态。
6. 确认切换成功后，移除旧公钥及关联配置，并记录轮换结果。
7. 若切换失败，系统按照预定策略重试或进入安全恢复流程，避免无期限保留已失效密钥。

如果确认私钥泄露，处理优先级应由正常轮换提升为安全撤销，及时阻断旧凭证并调查可能受到影响的节点。

## 十二、管理控制台与开放 API 模块

### 12.1 模块目标

管理控制台提供统一的企业网络和安全管理入口；开放 API 为客户端、自动化运维、云平台集成和第三方系统提供标准化操作能力。

控制台不应直接修改底层 WireGuard 配置，而应调用控制面业务接口，由业务服务完成校验、状态变更、任务创建和配置编排。

### 12.2 关键功能

- 企业、用户、设备、资源和网络管理。
- 访问策略配置、发布及执行状态查询。
- 隧道、节点、网关和中继状态监控。
- 连接记录、安全事件和操作审计查询。
- API 凭证管理、调用权限控制及限流。
- 资源批量导入、批量配置和自动化操作。
- 操作确认、变更预览和高风险操作保护。

### 12.3 关键技术

统一 API 契约。 对外管理接口采用 REST API，服务间通信可采用 gRPC。接口应统一错误码、分页方式、鉴权上下文和幂等操作约定。

管理权限与网络权限分离。 管理员能够编辑某项策略，并不意味着管理员当前设备自动获得目标网络访问权。涉及高风险操作时，可增加二次认证、审批或双人复核。

异步任务处理。 大规模配置发布、节点批量升级和网络拓扑变更可能耗时较长，应采用异步任务机制。API 返回任务标识和当前状态，控制台通过轮询或事件通知展示处理进度。

### 12.4 业务流程：管理员发布网络变更

1. 管理员进入控制台，选择待修改的网络、资源或策略。
2. 前端调用管理 API，服务端验证管理员身份、目标资源的管理范围和操作权限。
3. 业务服务执行参数校验，并生成变更预览，包括受影响节点、资源和现有授权关系。
4. 对需要审批的操作，变更进入待审批状态；审批通过后才进入发布流程。
5. 控制面保存新版本并创建配置分发任务。
6. 控制台展示节点同步情况、失败原因和未完成任务。
7. 操作完成后生成审计记录；若部分节点未能应用配置，则明确显示部分成功状态，而不是直接宣告全部成功。

## 十三、监控、审计与安全运营模块

### 13.1 模块目标

监控模块关注系统运行状态，审计模块记录可追溯的管理和安全活动，安全运营模块负责发现异常并推动处置。三者可以共享事件基础设施，但应保留不同的数据语义和访问权限。

### 13.2 关键功能

- 控制面 API、数据库和后台任务的运行监控。
- WireGuard 节点、隧道握手、流量和配置同步监控。
- 认证失败、设备撤销、异常访问和策略拒绝事件记录。
- 管理操作审计、策略变更记录和配置发布记录。
- 节点离线、隧道中断、同步失败和异常流量告警。
- 告警确认、处理记录、恢复状态和事件关联。
- 审计数据查询、保留周期管理和导出权限控制。

### 13.3 关键技术

结构化日志。 采用统一字段记录企业实例、组织、用户、设备、节点、请求 ID、事件类型、时间戳和结果等信息。避免将密码、令牌、私钥或其他敏感数据写入日志。

指标与事件分离。 指标用于描述系统运行状况，例如连接数、握手时间、配置同步延迟；事件用于记录离散事实，例如设备被撤销、策略被修改或访问被拒绝。

审计记录可靠性。 对关键安全操作，应确保审计事件与业务操作之间具备明确关联。可采用事务内写入、事务性 Outbox 或可靠事件投递方式降低业务变更成功但审计事件丢失的风险。

敏感操作可追溯。 审计记录应明确记录操作者、操作对象、变更前后状态摘要、结果和关联任务。审计数据的修改、删除及导出也应受到严格控制。

### 13.4 业务流程：安全事件处理

1. 认证服务、策略引擎或网络节点发现异常事件。
2. 事件被统一归类，附带相关组织、身份、设备、节点和请求关联标识。
3. 告警规则判断事件级别，并根据条件执行通知或自动化处置。
4. 对设备失陷、密钥泄露等高风险事件，可触发设备隔离、凭证撤销、策略收紧或连接阻断。
5. 系统将处置任务发送给配置分发模块，跟踪各节点执行结果。
6. 安全运营人员查看事件时间线、执行调查并记录处置结果。
7. 事件关闭后保留审计记录，用于后续调查、合规审查和策略改进。

自动化处置必须有明确的触发条件、权限边界和失败处理机制，避免误报直接造成大范围网络中断。

## 十四、持久化存储与异步任务模块

### 14.1 模块目标

持久化存储模块负责保存 VeloTrust 的业务数据、期望配置、任务状态和审计记录；异步任务模块负责处理配置分发、节点同步、密钥轮换、策略撤销及其他需要跨节点执行的操作。

控制面是分布式系统，数据库记录的期望状态与节点的实际运行状态可能短暂不一致，因此必须将业务数据持久化和运行状态同步作为两个不同的问题处理。

### 14.2 关键功能

- 保存企业基本信息、组织、用户、设备、网络、资源和策略等业务数据。
- 管理隧道、Peer、路由和节点配置版本。
- 持久化配置分发任务及执行结果。
- 支持任务重试、超时、取消和失败补偿。
- 记录关键业务事件和安全审计事件。
- 支持数据库备份、恢复及数据迁移。
- 为节点状态和连接指标提供独立的查询与聚合能力。

### 14.3 关键技术

建议根据数据类型选择不同的存储方式：

| 数据类型    | 建议技术               | 主要用途                |
| ------- | ------------------ | ------------------- |
| 核心业务数据  | PostgreSQL 或 MySQL | 企业组织、用户、设备、资源、策略及关系数据 |
| 短期缓存    | Redis 等缓存系统        | 会话辅助状态、热点数据、限流及短期协调 |
| 异步任务与事件 | 持久化任务表、消息队列        | 配置发布、撤销、重试和节点事件     |
| 运行指标    | Prometheus 等监控系统   | 连接数、延迟、错误率及资源使用情况   |
| 日志与审计检索 | 日志平台或独立审计存储        | 事件检索、故障分析及安全调查      |

不必在系统初期引入所有基础设施。可以先以关系型数据库、持久化任务表和基础监控搭建完整闭环，随着节点规模和查询负载增长，再拆分消息队列、指标存储和日志检索。

一致性设计方面，应避免通过多个独立数据库写操作模拟一个原子业务事务。例如，策略发布、版本记录和待分发任务之间需要明确的事务边界，可采用事务性 Outbox 或等效机制，保证业务状态提交后不会遗漏必要的配置分发任务。

### 14.4 业务流程：配置任务可靠执行

1. 管理员提交配置变更，业务服务验证参数和操作权限。
2. 数据库事务保存新的期望状态、配置版本及对应的待处理任务。
3. 任务调度器获取待执行任务，并根据目标节点和任务优先级安排执行。
4. 分发服务将任务通知发送至节点，节点拉取配置并执行更新。
5. 节点返回执行结果，服务端持久化任务状态和实际配置版本。
6. 超时任务进入重试或故障处理流程，重复执行时通过幂等标识防止产生重复副作用。
7. 后台对账任务定期比较期望状态与实际状态，发现偏差后创建修复任务或告警。
8. 当所有必需节点完成变更后，任务进入成功状态；如果部分节点失败，则保留部分成功状态及失败明细。

对于撤销任务，不能仅因消息已入队就认为撤销完成。应记录实际生效进度，并针对长期离线的节点制定明确的隔离或重新接入规则。

## 十五、高可用、部署与运维模块

### 15.1 模块目标

部署与运维模块负责保障控制面和数据面在节点故障、网络异常、配置错误及升级过程中持续提供服务。

VeloTrust 应区分控制面高可用和数据面高可用：控制面短暂不可用时，现有隧道可能仍能继续传输；但新设备注册、策略变更、配置更新和即时撤销能力可能受到影响。具体行为取决于客户端、节点和授权配置的实现。

### 15.2 关键功能

- 控制面多实例部署和服务健康检查。
- 数据库高可用、备份及恢复演练。
- 网关和中继节点的冗余部署。
- 节点升级、配置发布和版本兼容管理。
- 资源容量、连接规模及带宽监控。
- 故障告警、恢复演练和应急处置。
- 配置回滚、节点重新注册和网络状态恢复。

### 15.3 关键技术

控制面无状态化。 尽可能将认证 API、资源查询和策略服务设计为可横向扩展的服务实例，业务状态存储在数据库或明确的状态服务中。对于连接型服务，需另外考虑 gRPC 长连接、事件订阅和节点会话的恢复。

数据面独立扩展。 根据企业网络规模和流量需求独立扩展访问网关与中继节点，避免控制面 CPU 或内存不足直接影响数据转发能力。

升级兼容。 节点配置协议需要具有版本标识，并明确控制面和节点之间的兼容范围。升级过程应先验证新版本，再逐步发布，避免一次性推送导致大规模断网。

故障模式设计。 对数据库故障、控制面不可达、节点离线和配置错误分别制定恢复策略。特别是安全撤销与可用性之间的取舍，应明确哪些状态允许短暂延续、哪些状态必须立即拒绝访问。

### 15.4 业务流程：节点故障与恢复

1. 监控系统发现网关或中继节点心跳丢失、指标异常或服务探测失败。
2. 系统判断是否达到故障阈值，避免因瞬时网络抖动触发频繁切换。
3. 控制面将节点标记为异常，并根据拓扑和策略判断是否需要切换到备用节点。
4. 对具备备用路径的业务，更新相关路由或连接配置，并通知客户端重新连接。
5. 若无法自动恢复，系统告警并保留受影响的资源、节点和任务信息。
6. 故障节点恢复后，重新验证节点身份和配置版本。
7. 节点获取当前有效配置，完成状态对账后再恢复正常服务。
8. 记录故障持续时间、影响范围、切换结果和恢复过程。

对于安全敏感节点，恢复服务前还应检查其密钥、版本和安全状态，不能仅因进程重新启动就自动恢复全部访问权限。

## 十六、核心业务端到端流程

前述模块需要形成完整的业务闭环。以下三个流程是 VeloTrust 首期实现时最重要的端到端场景。

### 16.1 场景一：企业部署初始化并开放受控网络访问

1. 企业初始化

   平台管理员初始化当前部署的企业资料、企业管理员和基础安全策略。
2. 用户与设备注册

   企业管理员添加用户；用户登录客户端，完成设备注册、身份绑定及必要的设备审批。
3. 网络与资源纳管

   管理员创建企业网络，登记服务器、业务系统和访问网关，完成网段冲突及路由可达性检查。
4. 制定访问策略

   管理员明确用户或用户组可访问的资源、协议、端口和适用条件，发布策略版本。
5. 配置编排与分发

   控制面计算授权结果，生成 Peer、路由和 ACL 配置，分发至客户端和相关网关。
6. 建立隧道与验证业务

   客户端建立 WireGuard 隧道，网关执行网络访问控制，并通过目标连通性检查验证访问结果。
7. 持续监控与审计

   系统记录配置版本、连接状态、访问结果及管理操作，为后续变更和故障排查提供依据。

该流程的关键不是单纯完成一次隧道连接，而是确保从企业身份、设备可信、资源定义、策略授权到网络执行之间存在可验证的关联。

### 16.2 场景二：用户申请访问一个新资源

1. 用户登录客户端，查看当前可访问的资源目录。
2. 用户选择目标资源，系统检查其是否已纳管，以及当前用户和设备是否满足申请条件。
3. 如果该用户尚未获得访问权限，系统根据企业配置决定直接拒绝，或创建访问申请单。
4. 对需要审批的申请，资源负责人或安全管理员审核访问目的、授权范围和有效期。
5. 审批通过后，系统创建有期限的授权记录，并将其纳入策略计算。
6. 策略引擎生成授权决策，网络控制模块生成相应的配置变更。
7. 配置分发模块将变更同步到客户端和网关，并确认必要节点已应用。
8. 客户端刷新有效资源列表，用户发起连接。
9. 网关根据已生效的访问控制规则决定是否转发流量。
10. 到期后，授权自动失效，系统移除相关访问规则，并跟踪撤销是否真正生效。

建议将审批结果、有效授权和数据面执行状态分开记录。 审批通过不等于授权配置已经下发，配置下发也不等于访问已成功。

### 16.3 场景三：用户离职、设备失陷或权限撤销

触发撤销事件

用户离职、账户禁用、设备失陷、策略撤销或授权到期

立即更新可信状态

使用户会话、设备凭证或授权记录进入失效状态

生成撤销任务

计算受影响的客户端、Peer、路由及网关访问规则

执行网络隔离

更新配置、删除访问规则，必要时阻断现有连接

验证撤销与记录审计

跟踪节点确认、处理失败任务并形成可追溯记录

撤销处理应遵循以下原则：

- 先阻止新的授权和访问，再完成后台清理。 对高风险事件，不应等待所有异步任务完成后才改变用户或设备的有效状态。
- 区分身份撤销与网络撤销。 令牌失效并不必然关闭已建立的 WireGuard 隧道；移除 Peer 也不必然清除所有已有连接跟踪状态。
- 定义明确的撤销时效目标。 例如，根据安全要求规定高风险撤销应在多少秒内完成，并通过节点确认及实际访问测试验证。
- 处理离线节点。 如果节点无法收到撤销命令，应根据风险级别阻止其重新接入、限制旧授权继续使用，或者采取其他预先定义的隔离措施。

## 十七、关键技术选型与实现边界

结合 VeloTrust 以 Go 和 WireGuard 为核心的技术路线，可以采用以下技术组合。

| 技术领域   | 推荐方案                             | 实现重点                          |
| ------ | -------------------------------- | ----------------------------- |
| 后端开发   | Go                               | 模块边界、并发控制、服务生命周期及可观测性         |
| 管理 API | REST API                         | 管理操作、资源查询、统一错误处理              |
| 服务间通信  | gRPC                             | 认证上下文、节点控制、超时和重试              |
| 数据面隧道  | WireGuard                        | Peer 管理、加密传输、隧道地址及 AllowedIPs |
| 策略执行   | 主机防火墙、网关 ACL，必要时七层代理             | 与策略决策结果一致，限制实际可达范围            |
| 业务数据库  | PostgreSQL 或 MySQL               | 事务、约束、索引和配置版本管理               |
| 短期状态   | Redis 等                          | 缓存、限流及辅助协调，不作为唯一的关键审计存储       |
| 可靠任务处理 | 持久化任务表，按规模引入消息队列                 | 幂等、重试、补偿和最终一致性                |
| 身份集成   | OIDC、SAML、企业目录                   | 外部身份联邦、身份映射及会话生命周期            |
| 密钥保护   | 本地安全存储、KMS/HSM（按部署条件）            | 私钥保护、凭证轮换及权限隔离                |
| 监控与日志  | Prometheus、OpenTelemetry、结构化日志平台 | 指标、链路追踪、告警和安全审计               |

上述选型是技术实现建议，不意味着每个模块都必须单独部署为微服务。对于初期版本，建议优先实现模块化控制面，再根据负载、可靠性要求和团队维护能力拆分服务。

### 建议的核心服务边界

管理与身份服务

组织管理、用户认证、设备身份、资源目录、管理 API

策略与授权服务

策略管理、授权计算、策略版本、权限撤销

网络控制服务

节点注册、隧道编排、地址分配、配置生成及分发

节点代理与数据面

配置接收、WireGuard 管理、路由与 ACL 执行、状态上报

运维与安全运营服务

审计、指标、告警、异步任务、配置对账及故障恢复

建议优先把网络控制服务与节点代理的接口定义清楚。控制面应操作抽象的节点、Peer、路由和访问规则，而不直接依赖某个操作系统命令的输出格式。这样可以为后续支持 Linux 网关、容器环境、不同云平台及客户端版本演进保留空间。

## 十八、实施阶段与验收标准

建议分阶段建设，每个阶段都形成可验证的业务闭环，而不是只完成数据库表和管理页面。

| 阶段          | 核心建设内容                                 | 主要验收标准                |
| ----------- | -------------------------------------- | --------------------- |
| 第一阶段：基础控制面  | 组织、用户、身份认证、设备注册、资源管理、基础策略              | 可完成用户登录、设备注册和资源授权管理   |
| 第二阶段：基础网络接入 | WireGuard 节点、地址分配、Peer 管理、隧道建立、路由与 ACL | 授权用户可以访问指定资源，未授权流量被阻断 |
| 第三阶段：配置闭环   | 策略版本、配置分发、状态确认、任务重试、状态对账               | 配置变更可跟踪，失败节点可发现并恢复    |
| 第四阶段：企业级安全  | 多因素认证、密钥轮换、即时撤销、审计、风险告警                | 用户或设备撤销后，访问能力按约定时限失效  |
| 第五阶段：多云与高可用 | 多站点组网、中继、冗余网关、自动故障恢复                   | 节点故障可检测，备用路径和恢复行为可验证  |
| 第六阶段：规模化运营  | 性能优化、容量规划、自动化部署、监控和运维体系                | 在目标并发、吞吐和故障条件下达到约定指标  |

验收时至少应验证以下几类指标：

- 安全性：未授权用户无法建立受保护的访问；不同安全域之间不存在未授权的网络访问路径；设备撤销后不能继续使用有效访问权限。
- 功能性：用户注册、登录、设备接入、策略发布、资源访问和撤销形成完整闭环。
- 可靠性：控制面重启、节点短暂离线和重复配置任务不会造成不可恢复的配置不一致。
- 可观测性：能够区分认证失败、策略拒绝、隧道失败、路由故障和目标服务不可达。
- 性能：针对目标终端数、在线节点数、并发连接数、配置变更频率和隧道吞吐量制定测试指标。
- 可运维性：能够查询节点实际配置版本、未完成任务、撤销传播状态和故障恢复记录。

具体性能阈值、撤销时限及高可用目标，应结合预计终端规模、业务流量、部署地域和基础设施条件制定，不宜在缺乏负载基准的情况下直接承诺固定数值。

## 十九、总结

VeloTrust 的核心并不是单独部署 WireGuard，而是建立一套围绕身份、设备、策略和网络配置运行的零信任访问控制体系。

整体实现应围绕四条主线展开：

1. 身份主线：企业、用户、设备和凭证建立可信关联。
2. 授权主线：将用户、设备、资源和环境条件转化为明确的访问决策。
3. 网络主线：通过 WireGuard、网关、路由和 ACL 将授权结果落实到实际数据面。
4. 运营主线：利用配置确认、状态对账、撤销、审计和监控，保证安全策略持续有效。

其中最关键的工程问题，是如何让控制面维护的期望授权与数据面实际执行的访问控制保持一致，并在策略变更、设备失陷、节点故障和配置分发失败时，仍然具备可验证、可追踪和可恢复的处理机制。

只有把这四条主线形成闭环，VeloTrust 才能从基础的 WireGuard 组网工具演进为具备企业级身份管理、动态访问控制、多云组网和持续安全运营能力的零信任访问平台。
